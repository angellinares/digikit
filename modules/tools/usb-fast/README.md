# digikit/usb-fast

File uploads on a USB bulk interface, several times faster than SysEx. A run-time module (`.dkm`) in C; it needs `core/usb-bulk` (the adapter that adds interface 2,
EP2 OUT and IN, to the USB MIDI mode) and, on the Digitakt II, `core/plusdrive-write` for the +Drive. Plan: `docs/plans/usb-fast.md` section 5 and
`docs/plans/usb-fast-hardware.md` (step 4). Selected, the device re-enumerates once at boot and offers the bulk interface; not selected, USB is stock and SysEx
does everything as before. In USB AUDIO/MIDI mode macOS asks once to allow the accessory when it first sees the Fast USB interface; allow it. Windows stays on SysEx for now (no WinUSB descriptor yet).

- **SysEx**: `USB_FAST_NONCE` (0x36, range `usb_fast` of `sdk/sdk.toml`): body 8 bytes, empty reply. `STATUS` (0x37) is a debug aid: 20 words, word 8 is `dk_usb_bulk_state` (the host reads its wrong-mode bit); body `'S' ...` is the speed mask (below). STATUS words 18 and 19 are the staging reservation in bytes and the ring slots of the live block, for the hardware A/B. The host sends random bytes, then asks INFO on each
  candidate USB device and keeps the one that returns them (the USB serial strings are the same on every unit).
- **Speed switches**: `STATUS` body `'S' [bit [0|1]]` reads the four switches or sets one (RAM only, all on at boot, never saved) and replies the mask (u32). The later levers (batch commit, DT2 +Drive write cuts, copy/write overlap) have no switch. Bits 0 and 2 live in the runtime's speed word (`dk_debug_speed_flags`), bit 1 in core/usb-bulk (`dk_usb_bulk_ring`), bit 3 in core/sdhc-large (`dk_sdhc_large_ctl`); setting a bit of an adapter that is not in the image is E_STATE. Bit 0: hash once (DN2 store: the received bytes are not hashed when BEGIN carries the host hash; the close's card read-back is the only hash and must equal it), bit 1: USB receive ring, bit 2: the read-back hash runs on the runtime's helper task while the next piece is read (DN2 store and the DT2 +Drive close hash), bit 3: large card commands. STATUS bodies dispatch by their first byte through `status_tab` in `usb-fast.c`: one line per tag.
- **Copy/write overlap** (runtime 0.8.3, docs/plans/usb-fast-batch.md E5): with the 1 MiB reservation, a file larger than 512 KiB is staged in two halves of 512 KiB. A half that fills becomes the pending write and the stream goes on in the other half. The write goes out from the step loop (`ov_service`); before it, `pump()` runs in plan mode over the frames the receive ring holds already: it records each DATA body copy (destination in the other half, source in the receive buffer) instead of making it, and the module starts them on the runtime's helper task with `dk_helper_run` (pure compute, no import). `dk_files_write` then blocks the I/O task while the helper copies; `dk_helper_wait` collects it and the receive buffers go back to the adapter. A DATA that fills a half is answered at once (accepted); a failed write is sticky (`acc_err`) and shows on the next DATA or END, as before. Replies stay in order, the E_BUSY retry (3 tries) and the 20 s session expiry work as before, and the 256 KiB tier keeps one buffer. A file of 512 KiB or less, and the 256 KiB and fallback staging tiers, keep one buffer and no helper. Measured (finding 134): a 9.8 MB file goes from 3.67 to 4.37 MB/s on the DN2 and from 3.68 to 4.01 MB/s on the DT2.
- **OUT-only mode and `'R'`**: when `dk_usb_bulk_state` has `DK_USB_BULK_OUT_ONLY` (USB AUDIO/MIDI with the bulk OUT endpoint only, no bulk IN), the job never calls `dk_usb_bulk_send`: replies stay in the reply queue (16). `STATUS` body `'R'` (one byte) drains it: the reply body is zero or more complete reply frames (`'DKB1' | cmd|0x40 | seq | status | len | body`), oldest first, concatenated, at most 879 bytes, a frame never split; an empty body means none pending. The poll wakes the job. The parse throttle (nothing is parsed with 15 or more queued replies) stays, so a host that does not poll is NAKed, not overrun. `'R'` returns an empty body outside OUT-only mode. Lifecycle in OUT-only mode: at boot the job does not enable the bulk session (no ring, no staging buffer). `SET_NONCE` (0x36), which the host sends before INFO, records the time and wakes the job; the job reserves the staging buffer and calls `dk_usb_bulk_enable`. The host's INFO is a bulk OUT transfer that the controller NAKs until the ring is primed, so it needs no retry. INFO clears the reply queue (replies of an old session are dropped). 21 s after the later of the last `SET_NONCE` and the last file activity the job calls `dk_usb_bulk_disable`, drops the stream and the file and frees the staging reservation; the next `SET_NONCE` starts again. Port 2 (pair mode) keeps the enable-at-boot behaviour. The queue slots and indices are shared by the job and the MIDI task and changed with the interrupt mask on. INFO `flags` bit 0 is set in this mode: replies come over SysEx (`'R'` poll).
- **Bulk protocol** (`[protocol.bulk]`): request `'DKB1' | cmd | seq | flags u16 | len u32 | body`, reply `'DKB1' | cmd|0x40 | seq | status i16 | len u32 | body`.
  INFO replies `version, flags, window, reserved, data_max, align, nonce[8]`: `window` is the receive window in DATA frames of 64 KiB (core/usb-bulk's ring: 12 with 60 slots; 0 from an older device or with the ring off: the host keeps 2 in flight). A host that asks INFO keeps that many DATA requests in flight (`BulkSession`, `dkbulk`); a reply still means "accepted": the bytes are in the ring or the staging buffer. BEGIN (`root, path, size, hash4`; flag REPLACE) opens a file with `file_create`, DATA
  (`offset, bytes`) writes with `file_write`, END closes with `file_close` and replies `hash|1 (4 bytes) | pending u16 | reserved u16` (an older device sends the 4 bytes only), ABORT drops the open file (pending files stay). VERIFY is reserved and answers
  `E_PROTO`: the host verifies over SysEx.
- **Batch commit** (runtime 0.8.3, docs/plans/usb-fast-batch.md B): BEGIN flag `DEFER` (0x0002) creates the file with `DK_FILE_DEFER`. END verifies it (card read-back and hash, as ever) but the file is only pending: its extent is kept, no table names it. `pending` in the END reply is the number of pending files; 0 means everything sent so far is committed (the runtime commits all pending files at a deferred BEGIN that would pass 16 files or 16 MiB, and BEGIN returns the error if that commit fails; a pending file whose replaced file is being read stays pending and is counted). COMMIT (0x07, no body) calls `dk_files_commit`: one table commit for all pending files; its reply body is `pending u16 | reserved u16`. The runtime also commits 1 s after the last file call, at job end and at unload, so an unplug or a host crash loses no file that END reported verified once a second has passed. A power cut before the commit loses the pending files (the space is free after boot). An older device ignores DEFER and answers COMMIT with E_PROTO: the host reads both as committed. On the DT2 +Drive the files are named at END (`pending` is 0) and COMMIT runs the deferred hash-table rebuild.
- **Stream**: frames are cut by their length field, not by USB buffers: a frame may span receive buffers and a buffer may hold several frames. Each frame is copied
  into one 16-byte-aligned buffer (so `file_write` gets an aligned pointer) and each receive buffer is released as soon as its bytes are copied. A bad magic or a
  length over `data_max + 4 + frame_slack` is fatal for the stream: the module replies `E_MSG` for the seq it saw, drops what it holds and the open file, and reads
  the next bytes as a new stream.
- **Busy**: a `file_*` call that answers `E_BUSY` is called again (the runtime waits 1 ms) up to 3 times (BEGIN 400 times, about 0.4 s: the +Drive staging folder is removed after an idle session), then the host gets `E_BUSY`. No receive buffer: the job
  sleeps and the adapter wakes it; the host is NAKed while the ring is full. Replies are queued (16): a send that finds both slots in flight does not stop the stream, so a host that sends 12 frames before it reads a reply never deadlocks the ring.
- **Staging before ring**: the module reserves its staging buffer (1 MiB, else 256 KiB) before the adapter allocates its receive ring (in the enable step), keeps it for the session and frees it when the adapter's buffers are gone or at unload; each file uses as much of it as it needs. On a tight heap the ring then takes the smaller tier, not the staging buffer. Static evidence: the 32 MiB buddy heap has about 27 to 29 MB free with a project loaded and a largest free block of 16 MiB (findings 41, 47), so 1 MiB + 1 MiB is expected to fit on both devices (the staging buffer comes first from the module arena when that can give it).
- **Reset**: a bus reset or a disconnect (the reset count of `dk_usb_bulk_state` changes) aborts the open file and clears the parser.
- **Enable**: the job calls `dk_usb_bulk_enable` until it succeeds: the module's own tick wakes it four times a second while the device is not in a bulk mode, a mode switch is settling or no session is enabled. A device that stays in a mode without bulk for 2 s ends the session (buffers freed), and a switch between USB MIDI (the pair) and USB AUDIO/MIDI (OUT-only) ends it at once; the next enable follows when the mode is usable (OUT-only: at the next nonce). The runtime's file-session expiry is not mirrored: the next write answers `E_STATE`.
- **Idle session**: the runtime drops a write session with no write for 20 s; the job frees its staging buffer 1 s later.
- **Build flags** (`src/c/uf.h`): `UF_TRACE`, `UF_BENCH` (the storage bench, `src/c/uf-bench.c`) and `UF_KNOBS` (STATUS 'A', the staging buffer test knob) are 0 in shipping builds; the staging buffer test skips its forced-size cases without `UF_KNOBS`.
- **Unload**: `fini` disables the interface and cancels the job; the runtime aborts a file the job leaves open.
- **Test**: `tests/usb-fast.device.test.ts` (emulator, both devices) over `EmuBulkLink` of `packages/dk-session`.
