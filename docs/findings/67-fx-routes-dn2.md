## The DSP send mix over the voice slots **[D]**

The Digitone II has no track buses before its master function. The engine renders 16 voice slots, a bus each (`0x257ee8 + 0x100 * v`, 32 left then 32 right floats), and the master function sums them into track buses of its own (`0x258f68 + 0x100 * t`, cleared and filled inside
the function) with a slot-to-track map (`0x257898`: 16 halfwords, slot `v` in half `v % 2` of word `v / 2`, low half first, sign extended). A track that sounds in several slots (a chord, release tails) is the sum of those slots. The hook is the same place as on the Digitakt II: the first instruction of the master function.

| What | DN2 1.12 (1.11 has the same bytes) | Anchor |
| --- | --- | --- |
| the hook | `FUN_1c1f1e`, first instruction `I7 = modify(I7, -16)` (48 bits), one caller at `0x1c305d`; reloc hash `f8858e98...4296` | `dsp.fx.send` |
| slot buses | `I4 = 0x257ee8` (literal at `0x1c1fa2`, +0x84 parcels from the entry), 0x100 bytes a slot | `dsp.fx.slotbus` |
| slot-to-track map | `I2 = 0x257898` (literal at `0x1c1f9f`, +0x81) | `dsp.fx.slotmap` |
| slot fade flags | `I5 = 0x2578b8` (literal at `0x1c1f9c`, +0x7e), 16 bytes, one a slot | `dsp.fx.fadetab` |
| FX return bus | `0x25b868` (literal at `0x1c20fa`, +0x1dc; written by the sends driver at `0x1c1d96`) | `dsp.fx.return` |

At the entry the sends driver has finished: the slot buses are intact and the return is written and not yet read. The master mixes the slot buses and the FX return with the same factor (14.126, `R8 = 0x416201a3`), so the return of a unity effect with amount 127 is the track's own sound
(measured below).

`fxsend-dn2.s` builds the send bus of a row as the Digitakt II object does (finding 62: the same row words, the same gain law `(byte / 127)^2` ramped over the block, the same guard `_fx_exec`, the same return add with fade) but sums slots: it first reads the 16 map entries into a table of tracks (`& 15`),
then for each slot adds `gain[track of the slot] * slot bus`; a slot whose track has the old and the new gain 0 is skipped. The old gains are kept per track (16 floats a row) and brought up to date once all slots have been mixed, so a track in two slots has one ramp. The object has 278 instructions (the part of the slot mix is `fxsend-slots.inc`). Per block it reads the 16 map entries and the 16 fade flags in every case and adds the mix loop of the Digitakt II (4 instructions a sample, software pipelined) for each slot with a gain; a slot with a fade flag is scaled first (next section). Instruction counts: Costs.

## The slot fade (`0x2578b8`) **[D]**

The master loop (`FUN_1c1f1e`, `0x1c1fa8` to `0x1c1fec`, 16 iterations) reads two tables of 16 entries in step: the map (`I2 = 0x257898`, a short word per slot) and a **byte** table (`I5 = 0x2578b8`, `R1 = DM(I5, M6)` is a byte load: the Type 3b access bits `l x w` are 0 0 0; the table follows the map by 32 bytes). The decode of the loop (the listing of the database is garbled in that stretch; the forms and fields were read one by one, the compute fields with `tools/sharc_dev/sharcfn/decode.py`):

- `R1 = leftz(R1)` on the flag byte sets SV when the byte is 0 (the result is 32), then `R1 = 0x3ee94c03; IF SV R1 = M5` (M5 = 0): the step is 0 for a flag of 0, else `0x3ee94c03` = 0.45567 = 14.126 / 31 (R8 = `0x416201a3` is the master factor). Any non-zero byte is the same flag.
- Sample 0 of the slot is added to its track bus (`0x258f68 + 0x100 * track`) as `x * F8`, then the gain goes `F2 = F8 - step` and falls by `step` after each sample: sample k is scaled by `14.126 - k * 0.45567`, i.e. 14.126 * (1 - k / 31); sample 31 is about 0. Both channels use the same gain. With the flag 0 the gain stays 14.126. The same loop with the step 0.375 (`0x3ec006c4`, factor 11.6256) mixes the slots into a second bus set (`0x259f68`, through a table of bus pointers at `0x257ea8`) at `0x1c2509`; it is not the track mix and the send hook does not touch it.
- The slot bus (`0x257ee8 + 0x100 * v`) itself is **not** faded: the fade is applied only while the master sums the slot into the track bus. The sends driver (`FUN_1c1738`) reads a second byte table 16 entries on (`0x2578c8`, a mute ramp of its own for its sends; not read by the send mix).
- **Who writes it:** `FUN_1c2712` (the per-slot update from the DSP frame), in a loop over the 16 slots (`0x1c2d10` to `0x1c2df3`, `R11` counts, `R9 = 16`). `I5` starts at `0x2578b7` (a `modify(I5, M7)` before the loop) and steps +1 in the delay slot of the branch `0x1c2d1b` (`modify(I5, M6)`), so for slot v the byte `0x2578b8 + v` and the byte of the second table (`+ 0x10`, through `M1 = 0x10`; `M2 = 0x11` clears it) are first cleared (`DM(I5, M6) = M13`, M13 = 0) and, when the slot's bit in the frame word `DM(I4 + 17)` says a new note (the same bit sets the per-slot byte `0x254b94 + v`) and a frame halfword differs from the one stored for the slot (`R2 = DM(I1, M0)` against `R0 = DM(I4)`, `comp` at `0x1c31bf`), set to 1 (`IF NE DM(I5, M5) = M14`, M14 = 1, at `0x1c31c7`).

**Measured in the emulator (stock image, `SHARC_WWATCH` on `0x2578b8` to `0x2578d7`, the map and `0x254b94`, bounded runs of 3000 DSP blocks, TRIG key presses from the keys 25 to 40):** 24 and 48 retriggers of TRIG 1 (alone, with PLAY stopped half way, and in keyboard mode with different pitches, the 16 slots all in use): the flag bytes never change (all notes on one track: the compared halfword is equal). Presses of the keys 25 to 40 in turn (16 tracks): the flag byte of slot v goes 0 -> 1 for **one block** when the slot is given to a note on another track, and the map entry of the slot follows **one block later** (the map write came 0.66 M instructions after the flag, the flag was cleared 6 k instructions after the map write). In that block the slot bus still holds the old voice's last block and the map still names the old track, so the master fades the old voice out over the block (a stolen voice does not stop with a click on its track), and the next block belongs to the new voice and the new track.

So the send mix needs the same fade, or a stolen voice leaves the send bus at full level and stops at the block edge. `fxsend-slots.inc` now reads the 16 flag bytes at the start of the slot mix (four word loads, `FEXT` of each byte into a table of 16 words) and, for a slot with a flag, `_fxs_fade` copies its bus into `_fxs_fbuf` scaled by w_k = 1 - k / 31 (w_0 = 1.0, w_(k+1) = w_k - 0.0322581 in float32, left and right with the same weights) and the mix reads that copy in place of the bus (so the gain ramp of the track applies to the faded sound; the order is `(x * w_k) * g_k` added to the bus). The weight is the master's gain divided by 14.126 (the send bus has no master factor, the return gets it); the step 1/31 in float32 (`0x3d042108`) is not bit for bit the master's 0.45567 / 14.126, so a send bus differs from "the master's fade of the same sound" by about 1e-7 relative (not measured on the engine **[O]**). Anchor `dsp.fx.fadetab` (the literal `I5 = 0x2578b8`, resolved by hash in 1.11 and 1.12, `devices/ports/dn2-1.11.toml` and `dn2-1.12.toml`).

What is still open **[O]**: the compared halfword at `0x1c31bf` was not named (a different machine on the slot does not matter here, only that the flag means "fade this slot's bus"); a real stolen voice (a sounding old voice on a slot that a note on another track takes) was not driven in the emulator, so the click of the unfaded send bus is derived from the loop, not heard.

## The page hooks and the Sound index **[D]**

`core/fxpages` has an object per device from the same source (`fxpages-dn2.s` is `fxpages-dt2.s` with the Digitone II's page numbers and addresses); `fxpages_info` is version 2 on both (the send words from byte 156).

| What | DN2 1.12 | Anchor |
| --- | --- | --- |
| the track FX key's page list | the FX view builder `FUN_40060e72` (hash `8fb90571...`), `move.l #list,D0` (6 bytes) at `+0x67a` (`0x400614ec`); the list `{16}` is rodata at `0x401e0464`; the count `moveq 1,D1` is just before | `cf.fxpages.keylist`, `cf.fxpages.keystock` |
| the end of the sound loader | `FUN_400dd34e` (hash `f766c42c...`), the common exit at `+0x3d8` (`0x400dd726`): `movem.l (SP),...; lea 0x20(SP),SP` | `cf.fxpages.sound` |
| the page accessor | `FUN_400c25d8` as before (finding 61); the send page is number 40 (page 37 + 3 effect slots), its name, title and level slot copied from page 16 (the cells `0x12d, 0x130, 0x12e, 0x12f, 0x44, 0x45, 0x43, 0x131`, level slot `0xa`, Sound owner 15) | `cf.fxpages.acc` |

Device facts (`[fx]` of `digitone-ii.toml`): `track_page = 16`, `send_template = 0x44` (the stock Delay send row), `sound_off = 0x34`, `sound_stride = 0x48b` (the 16 Sound objects lie inline in the kit object, `0x34 + 16 * 0x48b = 0x48e4 = array_off`; the stride is odd, so every halfword access is bytewise),
`send_indices = [100]`. The Sound array has 101 halfwords from `+0x14`; the setter `FUN_40037b74` accepts `idx < 0x65`, and index 100 has no row, is not saved by the Sound saver (it clears 0xb4 bytes and writes the 69 table entries) and is not copied into the DSP frame, as on the
Digitakt II for 69 and 70. The sound loader's own `memset` of the array zeroes index 100 on every kit load, which the hook counts (the amounts come back from the settings, finding 64). The value class of the knob rows is the Delay class (`0x75`) as before; the lock rule of the firmware reads the class table at
`0x4243425c` on this device (`0x4293c040` on the Digitakt II; 321 rows of 0x44 bytes by the accessor `FUN_400c257c`).

**Why one send slot [D, O].** A second send knob needs a second free Sound index. Index 65 has no Sound row, but the firmware copies it into the per-slot DSP frame and the DSP converts both halves of its word to floats (`0x1c2abc` ff.). The poke test (`pk_idx65_poke`, the stock firmware, TRIG 1 from a fixed DSP frame,
Sound[65] of all 16 tracks poked to 0 (reference), `0x3f00` and `0x7f00` before the note) gave a PCM bit-identical to the reference on FM TONE, FM DRUM, WAVETONE and SWARMER (about 95,600 active samples each), and the DSP frame word `0x25c5b4` changes on three of the four (it is the copy). So no stock machine uses index 65 in a way that
reaches the PCM with these values, but the consumer of the converted floats was not traced to the end (the function is the per-slot parameter conversion for every machine, hundreds of instructions), so index 65 is **not** used: `send_slots` stays 1, `send_indices = [100]`. Adding 65 later is two lines
in `devices/digitone-ii.toml` (`send_slots = 2`, `send_indices = [100, 65]`) after the consumer has been traced or an engine run with modulation on the knob has been compared. Report: `out/runs/patchkit/idx65/report.json` (derived data, not committed).

## Costs **[D]**

- **DSP instructions per block** (concrete core, `tests/patchkit/test_fx_send_dn2.py::test_the_slot_mix_costs`, the half test effect of about 210 instructions, steady block, identity map): one send row with 1 slot that has an amount 1679, 4 slots 2132, 16 slots 3944 (the Digitakt II's object: 1414 with one track, 3664 with 16; the 16 map entries and the 16 fade flags cost about 260 more); each slot with a fade flag costs 245 more for that block (4 slots, 1 flagged: 2377, all 4: 3112). A block with no send row costs the send hook the quick scan of finding 62.
- **Emulator CPU, the hook alone** (`coupled_ab`, DN2, scenario `trig1-taps`, 3 audio s, same binary, images through `--dsp-patch` from `pk_dsp_diff`: the DN2 `emulator` set with the send hook against the same set with the hook and its object left out of `core/fx` (a temporary edit of `module.toml`, restored); no effect row loaded, PCM hash equal in all runs; machine load 6 to 10 from other work): first run 3 pairs, DSP CPU per audio s 1.483 -> 1.446, paired ratio B/A 0.976 (0.975 to 0.979); second run 5 pairs, 1.462 -> 1.438, **ratio 1.006** (0.971 to 1.039, IQR 0.09 to 0.13). No cost is measurable on the Digitone II: the hook's block bars one generated region, whose few instructions the interpreter runs, probably below the noise of the machine (the Digitakt II measured 1.048 on a quiet machine, finding 62). The cost of an active send effect on the emulator was not measured here.
