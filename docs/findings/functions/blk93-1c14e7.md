# blk93@0x1c14e7 — 32-slot indirect scale/update, not a ring writer

- **Bounds**: entry `0x1c14e7`, return (`9b_abs`) at `0x1c15de`, delay slots
  finish at `0x1c15e3`. 98 instructions, matching `sharcinv.py`'s boundary
  (`entry=0x1c14e7 exit=0x1c15e3 n_insns=98`). Confirmed independently by
  `sharcflow.py`'s return list (nearest prior return `0x1c14e1`, nearest
  following return `0x1c15de`) and by walking `sharc_trace.py` to a clean
  `"return without followed call"` stop at `0x1c15de` — no unresolved branch,
  no truncation. **[V]**
- **Callers**: exactly one call in the image targets `0x1c14e7`: `FUN_1c2b24`
  at sw `0x1c30a0` (`25a_direct` + `3c`/`16a` linkage, returns to `0x1c30a7`).
  This is the call the task names — the last of the four in the per-frame
  render chain (`0x1c642a`, `0x1c18a6`, `0x1c207b`, `0x1c14e7`). **[V]**
- **Callees**: none. `calls=0`/`indirect_calls=0` in the inventory, and the
  trace never leaves the function — no `25a_direct`, no `9b_abs` indirect
  jump other than the terminal return. A genuine leaf. **[V]**
- **Label**: inventory label `IIR or recurrence`, confidence 0.5. Agrees with
  what's decoded below: several small buffers updated by repeated
  float-multiply against loaded/stored state, in place, no table lookup, no
  dual add/subtract network. **[D]** (label itself not independently
  re-derived, but the read is consistent with it.)

## What it computes

Reads three fixed RAM regions and one 32-entry pointer table, and performs
repeated **elementwise float-multiply-and-store-back** passes over them —
scaling/updating buffers of accumulated per-track state, not a table lookup,
not a cosine/exp evaluation, not an FFT butterfly. Two of five passes
dereference a **32-entry pointer table at `0x252d78`** (`= R12 + 0x3c`, inside
the shared per-frame context struct whose base `0x252d3c` the caller sets
once for the whole render-chain tail) to reach per-track buffers whose
addresses are **not present in the ROM image** — they are written at runtime,
so this static read cannot see what they point to. **[V]** for the
mechanism, **[O]** for the ultimate destination.

Register interface (`R12`/`R8`/`R4`, all set once by the caller before the
whole four-call chain, and `I2`/`I3`/`I5` inherited from the caller) is
**never dereferenced as an address in this function** — `R12`/`R8`/`R4` are
immediately reused as scratch float-multiply result registers, and `I2`/`I3`/
`I5` are spilled to the local frame at entry and restored at exit purely so
the function can reuse those specific address-register slots internally
(confirmed by a full walk of every `ureg-write`/`i-add` touching them: none
reads the caller's incoming value). Every pointer this function actually uses
is a **hard-coded literal** in the range `0x252d3c`–`0x254800`. **[V]**
(exhaustive scan of every `17a`/`17b` immediate and every `i-add`/`i-modify`
delta in the function; see Memory below for the full address list.)

Five passes, in order:

1. **256-count loop** (`0x1c1503`–`0x1c150c`): single stream at `0x252df8`
   (`= R12 + 0xbc`, immediately after the 32-slot pointer table, i.e. a
   `256 = 32 × 8` element array laid out right after it). Each iteration:
   load one float, multiply by a running product with the previous element,
   store two results back into the same slot and the slot 8 bytes on —
   i.e. a two-tap update over a stream, not a lookup. Runs at MODE1.PEYEN=1
   (SIMD, see below) throughout.
2. **2×16-count nested loop** (`0x1c1523`/`0x1c1529`–`0x1c1538`): three
   parallel streams at `0x254078`, `0x254378`, `0x254678`, each element
   multiplied against the next and stored back in place (32 elements per
   stream total). **[V]** structure, **[O]** what these three buffers hold.
3. **32-count loop** (`0x1c1547`–`0x1c15a3`, the big one, 92 sw-words of
   body): **the pointer-table pass.** Each of the 32 iterations loads
   `I3 = DM(I4)` where `I4` walks the table at `0x252d78` one slot (`+=M6`)
   per iteration — 32 slots, one per track, matching the orchestrator's
   32-per-track structure elsewhere in `FUN_1c2b24`. `I3` (the *value* read
   from the table, not its address) is then used as a base pointer for an
   8-times-repeated inner block: load through `I3`, multiply by a fixed
   constant `R0 = 1.0965000391` (bit pattern `0x3f8c5a1d`), store two results
   back through `I3` (offsets `0` and `+8` bytes, i.e. a stereo/two-lane
   write each inner step — 8 inner steps × 2 writes = 16 floats moved per
   track). MODE1.PEYEN is toggled on for the full 32-iteration span. Because
   the 32 table entries at `0x252d78` are RAM and not loader-covered
   (`sharcldr.py --addr 0x252d78`: *not covered by any loaded block*), their
   runtime contents — and therefore where the 16 floats per track actually
   land — cannot be read from the static image. **[V]** for everything up
   to "what `I3` is used for"; **[O]** for what `I3` points at.
4. **2×16-count nested loop, second instance** (`0x1c15b9`/`0x1c15bf`–
   `0x1c15ce`): three parallel streams again, this time at `0x253f78`
   (`I5`, freshly zeroed then offset), `0x254578` (reusing the `I3`
   register), `0x254278` (`I4`). Same cross-multiply-and-store-in-place
   shape as pass 2, over 32 elements. `R12`/`R8`/`R0` are the scratch
   float-multiply results here (confirming those "argument" registers are
   pure scratch, see above).
5. Epilogue: `I12` (return linkage), `I2`, `I3` restored from the frame,
   frame deallocated (`I7 += 16`), return.

**No named table, and no audio ring, is touched anywhere in this function** —
see Memory below for the exhaustive literal list. This is a real negative
(every constant operand was enumerated), not an absence of evidence, but it
does not clear the function of writing ring *data*: the two passes that go
through the `0x252d78` pointer table write to addresses this analysis cannot
see, and per the task brief, the ring-audio-data writer has never been found
anywhere in the image. This function's shape — 32 slots, one per track,
scaled by a near-unity constant and stored via a runtime pointer — is exactly
the shape a per-track-to-output-mix copy would have. It is a plausible
*candidate* for (part of) the missing writer, not a confirmed one. **[O]**

## Structure

```
0x1c14e7  prologue: I7 -= 16 (frame), save I2/I3/I5 to frame slots,
          I4 = 0x252df8, MODE1.PEYEN set, R2 = 3.1261000633 (0x40481206)
0x1c1500  loop (12a_imm, count=256): two-tap update over 0x252df8[0..255]
0x1c150f  MODE1.PEYEN clear
0x1c1512  I3 = 0x254678, I2 = 0x254378, I5 = 0 (17b)
0x1c151a  MODE1.PEYEN set
0x1c151d  7a: I4 = I5 (=0)
0x1c1520  loop (count=2) { loop (count=16): three-stream update
           0x254078 / 0x254378(I2) / 0x254678(I3) }         ; I4 = 0+0x254078
0x1c153e  MODE1.PEYEN clear
0x1c1541  I4 = 0x252d78                                     ; pointer table base
0x1c1544  loop (12a_imm, count=32):
0x1c1548    I3 = DM(I4, M5) [pre-modify]      ; dereference table slot
0x1c154a    I4 += M6                          ; next table slot
0x1c154d    MODE1.PEYEN set
0x1c1551    R0 = 1.0965000391 (0x3f8c5a1d)
0x1c1554..  8x repeated: load via I3(+8), multiply by R0, store to
0x1c1594    I3(+M5*4) and I3(+8)               ; 16 floats/track written
0x1c15a3  MODE1.PEYEN clear (loop-tail; also the 32-loop's real end)
0x1c15a6  I4 = 0x254278, I3(reused) = 0x254578
0x1c15ac  MODE1.PEYEN set
0x1c15b0  R2 = 6.1548910 (0x40c4f4de), R1 = 3.0774455 (0x4044f4de)
0x1c15b6  loop (count=2) { loop (count=16): three-stream update
           0x253f78(I5) / 0x254578(I3) / 0x254278(I4) }
0x1c15d4  MODE1.PEYEN clear
0x1c15d8  epilogue: restore I12, I2, I3 from frame; I7 += 16; return
0x1c15de  9b_abs return (M14, delayed) -> 0x1c30a7 in FUN_1c2b24
```

Every loop is **literal** (`12a_imm`), not register-counted: `256, 2, 16, 32,
2, 16` — six distinct loop-setup instructions, matching
`sharcinv.py`'s `loop_literal_values`. The `2×16` shape appears twice with
identical nesting (outer count 2, inner count 16), suggesting a two-channel
(stereo) split applied twice to different buffer pairs. **[V]**

`MODE1` bit `0x200000` is **PEYEN** (SIMD PEy enable, ADSP-SHARC+ PRM,
`out/refs/sharc-plus-prm/all.txt` around line 4611: *"bit 21 ... enables or
disables the PEy processing element ... SISD mode, using only PEx"* vs SIMD
with PEy on). The function toggles it on/off four times, always **on** for
the compute loops and **off** around the setup/store-only stretches between
them — consistent with running two-lane (stereo) SIMD only where two
channels are actually being produced together. **[V]**

## Memory

Every literal address this function references (exhaustive scan of all
`17a`/`17b` immediates and `i-add`/`i-modify` deltas in its span):

| address | role | loader-covered? |
|---|---|---|
| `0x252d78` | 32-entry pointer table (`R12+0x3c`) | no — RAM |
| `0x252df8` | 256-float stream (`R12+0xbc`, right after the table) | no — RAM |
| `0x254078` | stream A of pass 2 | no — RAM |
| `0x254378` | stream B of pass 2 (also `I2` init) | no — RAM |
| `0x254678` | stream C of pass 2 (also `I3` init) | no — RAM |
| `0x253f78` | stream A of pass 4 (`I5`) | no — RAM |

Checked with `tools/sharcldr.py out/sections/dt2-1.16/section_7_BLOB.bin

RAM, not loader-initialised ROM data. **[V]**

**None of the named tables are touched**: no cosine (`0x8055c440`/
`0x8055c640`), no 1024-float pair (`0x8055c890`/`0x8055d890`), no 829-float
exponential (`0x8045a6c8`), no 32-float table (`0x8045c3c0`), no stage-5

Does not touch the parameter frame (`0x2558dc` base, `0x2559b6+track*0x60`
per-track block, SRC page) — no literal in this function's span falls in
`0x2558xx`–`0x255axx`. **[V]**

## Interface

`R12`, `R8`, `R4` arrive with whatever the caller set once before the whole
`0x1c642a`/`0x1c18a6`/`0x1c207b`/`0x1c14e7` chain (`R12=0x252d3c`,
`R8=0x2506ec`, `R4=0x2412c8` at the call site `0x1c30a0`) but are **not
read** by this function — they are clobbered as scratch float-multiply
result registers in passes 3 and 4. `I2`, `I3`, `I5` arrive with whatever the
caller (or the previous call, `0x1c207b`) left in them, are spilled to the
local frame at entry, and are restored at exit — but their *incoming values*
are never read either; the function only uses them as free address-register
slots for its own hard-coded pointers. No output register is set up for the
caller (no write to `R0`-class return-value convention visible before the
epilogue's restores). Net effect: **this function takes no meaningful
arguments** as decoded — its entire behavior is driven by the fixed literals
in the Memory table above, plus whatever the runtime has written into the
32-slot pointer table at `0x252d78`.

## Open

- **What the 32-slot pointer table at `0x252d78` contains at runtime**, and
  therefore where pass 3's 16 floats/track ultimately land. This is the
  single biggest open question and the one that would confirm or rule out
  this function as (part of) the audio-ring writer. Settling it needs either
  a concrete/emulated run with the table populated, or finding the writer(s)
  of `0x252d78`'s 32 slots elsewhere in the image (a static search worth
  doing: `tools/refscan.py` for stores to `0x252d78..0x252df8` range,
  4 bytes at a time).
- **What the three-stream buffers (`0x254078`/`0x254378`/`0x254678` and
  `0x253f78`/`0x254578`/`0x254278`) represent.** Structurally a 3-way
  cross-multiply-and-store-in-place over 32 elements, twice, with different
  base addresses — could be a 3-coefficient smoothing/recurrence (matches
  the inventory's "IIR or recurrence" label) but the exact recurrence
  relation was not derived (would need concrete values for `M5`/`M6`/`M7`,
  which are register/runtime state the tracer could not resolve).
- **Concrete values of `M5`, `M6`, `M7`** (index-register steps used
  throughout) were never resolved — `--concrete-memory` reads loader-backed
  bytes, and these are RAM. Without them, the exact stride of the
  pointer-table walk and the exact element size of each stream is inferred
  from context (4-byte float, table stride consistent with 32×4=128 bytes
  exactly filling `0x252d78`–`0x252df8`) rather than directly read.
- The float constants (`3.1261000633`, `1.0965000391`, `6.1548910`,
  `3.0774455`) were not matched to any documented gain/scale table; flagged
  in case another function's notes recognize them (`6.1548910 ≈ 2 ×
  3.0774455`, exact — worth checking if these are a coarse/fine pair for
  the same parameter).
