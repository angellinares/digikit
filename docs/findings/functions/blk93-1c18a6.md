# blk93@0x1c18a6 — bounded RAM-word forwarder **[V][D][O]**

- **Bounds**: entry `0x1c18a6`, exit `0x1c1f7d` (exclusive), 654 instructions
  (`entry=0x1c18a6 exit=0x1c1f7d n_insns=654`).

## Verified bounded interval

In both DT2 1.15C and DT2 1.16, the identical raw instructions are:

- `0x1c18ed`, `100200252658`: Type14a `R2 = DM(0x252658)`.
- `0x1c18f3`, `100400254d9c`: Type14a `R4 = DM(0x254d9c)`.
- `0x1c191d`, `110200254d9c`: Type14a `DM(0x254d9c) = R2`.
- `0x1c1928`, `110400254d98`: Type14a `DM(0x254d98) = R4`.

Exhaustive canonical section-replay decoding and an independent raw review find
no intervening `R2`/`R4` destination or control transfer in this bounded
straight-line interval. The exact byte-proven assignments are therefore
`DM(0x254d9c) <- DM(0x252658)` and
`DM(0x254d98) <- old DM(0x254d9c)`. **[V]**

The automated Ghidra proof is deliberately scoped only to the R4 forwarding
path: within `FUN_001c18a6`, address-space-aware exact matching and raw p-code
agree on `ram 0x4a9b38 -> value -> ram 0x4a9b30` in both DT2 images. The R2
store slice returned no seeds. **[V]**

This is consistent with a two-word state/history shift, but semantic direction,
ownership, natural execution, and relation to machine type are not proven.
**[D][O]**

The mapping audit SHA-256 is
`24441e37f2933e1a8c561d5182b98f59812549e70df0b1251057f4b09e9f10d9`; the DT2
1.15C `0x252658` census artifact SHA-256 is
`1bbb5eaed7ec762d4a3692e851ae8b319e212b9f37ad8134c90c76f07b259b91`; and the
DT2 1.16 summary SHA-256 is
`ba1e830b04c8b79e283ff4305990d6bbf20d24b049297a2b52f97167400305ca`.
Each exhaustive even-offset canonical Type14a-g=0 census has exactly one direct
literal access to `0x252658`, the R2 reader at `0x1c18ed`, and no direct
Type14a writer. Computed/indexed/dual-memory stores, loader data, and
ColdFire/host writes remain possible. **[V]**

## Cross-device evidence

DN2 1.11 canonical scan proves exact encodings `0x1c19d7: R4=DM(0x25d010)` and
`0x1c1aaf: DM(0x25d00c)=R4`, with the same -4 source/destination address delta
as DT2. Scan SHA-256:
`fe05c06f323b41595e155d7238b92444c784e22e56ce04ed7a36420584cb5cb7`.
**[V]**

The containing DN2 block is `blk83@0x1c1738`, bounds
`0x1c1738..0x1c1e1f`, 659 instructions. Its vector is close to DT2: 3 calls,
204 loads/204 stores, 33 MACs, and one nested loop; DT2 has 654 instructions.
This is structural analogy only. HighFunction at the correct PCs has a
semantic-location mismatch and cannot prove that the same runtime value flows
between them. The earlier zero `0x254dxx` DN result is now an exhaustive direct-
Type14a result under that form/range, not architectural absence; DN uses shifted
RAM addresses in this candidate. **[D][O]**

## Caller context and open work

One documented static call is at `0x1c3090` from `blk93@0x1c2b24`, immediately
after R4/R8 frame setup; it is unconditional only within an already reached
caller. This neither establishes natural execution nor excludes indirect
callers. **[D][O]**

The direct local writer of `0x254d9c` is now known, and Ghidra dataflow proves
the R2 path too once `tools/ghidraq.py` stopped dropping memory-to-memory
`COPY` ops: `stores sw:0x254d9c` reports `sw 0x1c191d` as
`exact-constant-target` with `value_slice` root `ram 0x4a4cb0`. **[V][C]**

`0x252658`, `0x254d98` and `0x254d9c` all sit in one zero-FILL loader block
(DT2 block 18, `target_address 0x282412c0`, `byte_count 86216`, fill value 0,
covering `0x282412c0..0x28256388`; DN2 block 16 at `0x28241290` for its
shifted pair), byte-verified by a second agent across all three images with no
later block re-covering them. All three words are 32-bit zero at boot. **[V]**

An unbounded whole-image `stores sw:0x252658` finds no genuine direct writer in
either Ghidra project; the one match is a decompiler self-copy placeholder
with no raw instruction behind it. **[O]** **[C]** That sweep cannot see
indexed stores: the indexed DM forms (`15b`, `3c`, `4a`, `3a`, most `3b`) have
no SLEIGH semantics, so they emit no p-code, and the sweep returned no
`computed-or-unresolved` candidate anywhere in the image. The owner is
therefore still an indexed SHARC store, a ColdFire/host write, a DMA path, or
code outside Ghidra's function boundaries. I6+124 and external-table readers
remain open. **[O]**
