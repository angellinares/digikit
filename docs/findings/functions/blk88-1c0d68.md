# blk88@0x1c0d68 — shared exponential/mapping primitive (R4 selects a base: 2.0 / 10.0 / π), global scratch state

- **Bounds**: entry `0x1c0d68`, return (`9b_abs`, raw `0x083f343f`, matches
  the documented `JUMP(M14,I12)(DB)` return signature) at `0x1c0e93`, delay
  slots (`5b_move`+`15b`) finish at `0x1c0e99`. 127 instructions, exactly
  matching `sharcinv.py`'s boundary (`entry=0x1c0d68 exit=0x1c0e99
  n_insns=127`). Confirmed independently with `tools/sharcflow.py` run over
  the block's own extracted payload (`--base-sw 0x1c02a4`, the byte alias
  `0x28000000|(2*sw)` block base for `blk88`): the return list's entry
  `{'sw': 1838435, ..., 'after': 1838440}` (`0x1c0d68`) is followed by the
  next return `{'sw': 1838739, ..., 'after': 1838745}` (`0x1c0e99`), with no
  return in between over the depth-filtered aligned stream. **[V]**
  Caveat: a raw `0x083f343f` word also appears mid-body at what looked like
  offset `0x1c0d6c` under a *different*, wrong byte-alignment formula (see
  Open) — that was a tooling artifact of decoding against the wrong base
  file, not a second return; the correct per-block decode (`blk88_28380548.bin`,
  `base_sw=0x1c02a4`) shows no such instruction there. **[V]** (re-decoded
  and cross-checked against `sharcinv.py`'s own instruction stream, which
  agrees).
- **Callers**: **15 distinct calling functions**, 21 call sites total (two
  callers call it more than once). Confirmed by intersecting
  `tools/sharcflow.py` call lists for `blk93` (18 sites, `base_sw=0x1c13e6`)
  and `blk69` (3 sites, `base_sw=0xb80000`) against `target==0x1c0d68`, then
  grouping each site by the return-delimited function span that contains it
  (`sharcinv.function_bounds`). See **Caller analysis** below for the full
  table — this is the highest-value result in this note. **[V]**
- **Callees**: none. `calls=0`, `indirect_calls=0` in the inventory and in a
  direct re-scan of the block's own call/return list restricted to this
  span — a genuine leaf. **[V]**
- **Label**: inventory label `envelope or gain`, confidence 0.4, reason
  "float ALU ops dominate a moderate multiply count". Feature vector:
  `float_alu=48, float_mul=15, mac=3, dual_add_sub=1, int_alu=21, shifter=3,
  loop_literal=0, loop_register=0, mem_dm_load=31, mem_dm_store=11`.
  Consistent with what's decoded below (dense straight-line float compute,
  no hardware loop), but the concrete evidence (see below) points at
  something more specific than a generic envelope: a **shared exponential /
  power-mapping primitive**, reused for both pitch (note→frequency-ratio)
  and what looks like gain (dB-ish) computation depending on which constant
  the caller loads into `R4`. **[D]** — a strong, evidence-backed hypothesis,
  not a fully derived closed-form.

## What it computes

No hardware hard-loop (`loop_literal`/`loop_register` both 0 in the
inventory, and no `12a_imm`/`12a_ureg` instruction anywhere in the 127-word
span — checked directly). The body is dense straight-line float arithmetic
with several small conditional branches, bracketed by a fused
compute+register-save prologue and a fused compute+restore epilogue.

**The single dual add/subtract**, at `0x1c0de1` (`3a`, `i=4,m=4,u=0`,
`compute=0xFE0FC`): decoding the field per PRM Table 18-13's confirmed bit
layout (`Rs/Fs=[15:12]`, `Ra/Fa=[11:8]`, `Rx/Fx=[7:4]`, `Ry/Fy=[3:0]`,
opcode top nibble `0xF`⇒float) gives **`F0 = F15 + F12`, `F14 = F15 − F12`**,
computed in parallel with a `DM(I4,M4)` load into `R8` (`I4` was just pointed
at `0x241210`, the second of three small fixed cells — see Memory). This is
a plain register-pair sum/difference, not an indexed/strided array access —
**consistent with the image-wide conclusion that this idiom is a
paired-coefficient combine, not an FFT butterfly**; there is nothing here
resembling a bit-reversed or power-of-two-strided walk. **[V]** for the
decode (bit layout cross-checked against `tools/sharcspec/compute_table.json`
`Table18-13_DualAddSubFixed`, `dual_add_subtract`); **[O]** for what `F15`
and `F12` represent physically (not traced further upstream).

**Prologue** (`0x1c0d68`–`0x1c0d87`, 10 instructions): each is a fused
`compute ; DM(I7,M7)=Rn` (post-modify push), saving `R3, R5, R6(3c), R7, R9,
R10, R11, R13, R14, R15` to the stack — **`R4`, `R8`, `R12` are conspicuously
absent from the save list**, matching the task's convention that those three
carry arguments: the callee is free to read and clobber them. The parallel
compute half of the prologue is not idle filler — `sharc_trace.py`'s
per-instruction decode (`_compute`, operands resolved) shows real work:
`R12 = R12 and R12` (a self-AND, the classic zero/sign-test idiom — reads
`R12` as its first action), `R4 = R0 + 1`, `R5 = pass R0`, `R12 = R12 * R0`,
`R2 = pass R0`, `R7 = R7 and R0`, `R2 = compare(R2, R0)`, `R12 = R12 + R0`,
`R0 = R0 xor R0` (zeroing), `R0 = R0 * R0`, `R8 = R8 - R0`. **[V]** for the
individual decodes; **[O]** for the overall intent (looks like argument
validation/normalization touching `R12` and `R0` before the real body, but
the full data-flow was not traced end to end).

**Body** (`0x1c0d8c`–`0x1c0e8c`): no hardware loop; instead five
conditional branches (`8a_rel`, conditions `EQ`, `EQ`, `LT`, `AV`, `EQ`)
cluster right after the prologue (`0x1c0d8f`–`0x1c0da9`), then the float
compute core runs mostly straight-line: **15 float multiplies**
(`2a_short`/`4a`, opcode `0x30`, "plain float multiply"), the one dual
add/subtract described above, and roughly twenty more float add/subtract
instructions (`2a_short` opcode `0xD9`/`0xDA` appear 8 times — **not** in
`tools/sharcspec`'s public `aluop_32_40bit` table, so `sharc_trace.py`
reports them as "unsupported"; `sharcinv.py`'s classifier still buckets them
as float ALU since their opcode is `>=0x80`, which is where the "48 float
ALU ops" mostly comes from). A 0.0625 (`1/16`) float immediate appears at
`0x1c0e2c` — a clean power-of-two coefficient, consistent with a polynomial
term. Three more conditional branches (`GE`, `LE`, `LE`) cluster near the
end (`0x1c0e39`–`0x1c0e43`), plausibly a clamp/special-case selection before
the final result is written back. **[O]** — branch targets could not be
resolved with confidence (see Open); this is a structural read (branch
count, conditions, position), not a control-flow-graph.

One instruction (`0x1c0de4`, `8a_rel`, `cond=31` always, `j=1` delayed,
`b=1`) has a `reladdr` (`53770`) that does not resolve to an in-function
address under the plain PC-relative formula validated elsewhere in this
codebase (`sharcflow.py`'s `25a_pcrel` target math) — flagged, not
interpreted. **[O]**

**Epilogue** (`0x1c0e8f`–`0x1c0e97`): `I7 = I6` (restoring the stack
pointer from a saved copy) and one more `15b` load, then the return at
`0x1c0e93` (raw `0x083f343f`, delay slots `5b_move`+`15b`). **[V]**

### Evidence toward a specific algorithm

Every caller loads `R4` with one of essentially three float constants —
`2.0` (`0x40000000`), `10.0` (`0x41200000`), or `π` (`0x40490fdb`) — and a
second, much more varied value into `R8` (see the caller table). Two of the
`R4=2.0` callers (`0x1c4afe`, `0x1c4bf9`, and the render-chain caller
`0x1c642a` the task names) also load `R12=64.0`, `R1=60.0`
(`60`/`64` — MIDI-note-shaped integers, four semitones apart) and
`R8≈0.0833333` (**`1/12`**, the equal-tempered semitone fraction), with a
`float-clip` on `R12` right before the call. A different `R4=2.0` caller
(`0x1cbe19`) loads `R13=220.0` — **A3 concert pitch** — into the setup chain.
This is strong, if indirect, evidence that **this primitive evaluates
something like `base^x`** (a range-reduced polynomial `2^x`/`10^x`/`exp`-style
evaluator, matching the "no table touch, straight-line float ALU/MUL"
shape and the 0.0625 power-of-two coefficient), reused by the voice engine
for **pitch** (`base=2`, semitone fraction and note constants) and by other
callers for what is plausibly a **dB-style gain mapping** (`base=10`, small
signed values like `-2.4`, `-3.0`, `-0.9`, `-23.0` in `R8` — dB-shaped
ranges) and at least one caller for an angle-related use (`base=π`). **[D]**
— consistent, convergent evidence from five independent call sites, but no
polynomial coefficient or exact formula was derived; would need either a
concrete/emulated run with representative `R4`/`R8` values or hand-decoding
the remaining `0xD9`/`0xDA` opcodes against the vendor's public opcode table
(not available here) to confirm.

No loop of any kind (hardware `DO...UNTIL` or otherwise) was found in this
span — `loop_literal=0`, `loop_register=0` in the inventory, and a direct
scan of all 127 instructions found no `12a_imm`/`12a_ureg`. **[V]**

## Memory

Three small fixed cells, read (not obviously written) via `I4`/`M4`,
reloaded from **hard-coded literal addresses** at three separate points in
the function (`0x1c0d95`+`0x1c0dd3` both load the *same* address twice,
`0x1c0e75` a third time):

| address | role here | loader-covered? |
|---|---|---|
| `0x2411c8` | state cell #1, read 3x (`0x1c0d95`, `0x1c0dd3`, `0x1c0e75`) | no — RAM |
| `0x241210` | state cell #2, read once, feeds the dual add/subtract's DM operand | no — RAM |
| `0x241234` | state cell #3, read once | no — RAM |

Checked with `tools/sharcldr.py out/sections/dt2-1.16/section_7_BLOB.bin
--addr <addr> --addr-space byte`: all three report *"not covered by any
loaded block"* — RAM, contents not visible statically. **[V]**

These addresses are **hard-coded literals inside the callee**, not pointers
the caller passes in — none of the 15 callers' pre-call setup (see table
below) loads anything near `0x2411c8`–`0x241234`. That means, unlike the
per-track-struct pattern seen in other engine routines, **this primitive's
persistent state (if any) is a single global scratch area shared by every
caller**, not a per-voice struct threaded through `R12`. **[V]** for "no
caller sets these addresses" (checked every decoded call-site window);
**[O]** for whether the cells are read-only constants or genuinely mutated
scratch (no store to any of the three was found in this function, so if
they change at all it is from elsewhere in the image — not searched).

No named table is touched: no cosine (`0x8055c440`/`0x8055c640`), no
1024-float pair (`0x8055c890`/`0x8055d890`), no 829-float exponential
(`0x8045a6c8`), no 32-float table (`0x8045c3c0`), no stage-5 table
(`0x26bb68`), no 128-float pair (`0x256388`/`0x256588`), no audio ring
(`0x262138`/`0x262938`/`0x263138`/`0x263938`). Confirmed by
`classify_literal()` over every `17a`/`17b`/`16a`/`15a` literal in the span:
none fall in `NAMED_TABLES`, the ring set, or the `0x80xxxxxx` external
range. **[V]** This is a literal-operand scan; it does not rule out
reaching a table through the `I4` state cells if their (unknown, RAM)
contents are themselves pointers — no evidence either way. **[O]**

Does **not** touch the parameter frame (`0x2558dc` base,
`0x2559b6+track*0x60` per-track block): no literal anywhere in this span
falls in `0x2558xx`–`0x2560xx`. **[V]**

## Interface

`R4` and `R8` arrive as the two live float arguments (never saved in the
prologue, so freely read and clobbered); `R12` is read once right at entry
(self-AND, a sign/zero test) then also freely reused. No evidence of an
`I`/`M`-register pointer argument: none of the 15 callers sets an `I`/`M`
register to a literal in the `0x2411c8`–`0x241234` range or to anything else
distinctive right before the call (a few callers set `I2`/`I3`/`I5` for
*their own* surrounding code, not obviously handed to this callee). No
output register convention was confirmed — the function's last writes
before the epilogue are float-multiply/add results into `R4`-class scratch
registers, consistent with `R4` (or possibly `R0`) carrying the result back,
but this was not traced through to a caller-side consumer. **[O]**

for the shared computation, while `R8` (or a short chain the caller builds
into it) carries the actual per-call value. **[V]** for every literal in the
table (each individually decoded via `sharc_trace._compute`/`sharcinv`
against the correct per-block base file); **[D]** for the "R4 selects a
base" interpretation.

## Open

- **The full formula.** Convergent but indirect evidence (MIDI-note-shaped
  `60.0`/`64.0`, semitone fraction `1/12`, concert pitch `220.0`, `R4∈{2,10,π}`)
  points at an exponential/power-mapping primitive, but no polynomial
  coefficient or exact closed form was derived. Settling this needs either a
  concrete/emulated run with representative register values, or resolving
  the two repeated-but-undocumented float ALU opcodes (`0xD9`, `0xDA`, 8
  occurrences total) against a public SHARC+ source — they are not in
  `tools/sharcspec`'s `aluop_32_40bit` table.
- **Branch targets.** The nine `8a_rel` conditional/unconditional branches
  in this function were decoded structurally (condition, delay flag) but
  their `reladdr` targets did not resolve to sane in-function addresses
  under the PC-relative formula this codebase validates for `25a_pcrel`
  calls (`sharcflow.py`) — most computed targets land past the function's
  own exit, and one (`0x1c0de4`, `b=1`) computes an address far outside the
  block entirely. Either `8a_rel`'s relative base/scale differs from
  `25a_pcrel`'s, or these use a different addressing convention this task
  did not resolve. Needs a second, careful read of the `8a_rel` field
  layout (PRM figure, not guessed) before trusting any target here.
- **What the three state cells (`0x2411c8`, `0x241210`, `0x241234`) hold**,
  and whether anything else in the image writes them (not searched here —
  `tools/refscan.py` over that 0x241000-ish range would answer it). If they
  are read-only constants, they likely belong in the same
  "unnamed table" category as the audio rings; if they are mutated
  elsewhere, this primitive carries hidden global state shared by all 15
  callers regardless of which voice/track called it.
- **Output register.** No caller-side consumption of a result register was
  traced, so which of `R4`/`R0`/`R8` (if any) carries the return value is
  not confirmed.
- **A byte-alignment trap worth recording for the next reader**: a helper
  script (`listing.py`/`fullscan.py` in earlier scratch work) that computes
  blob file offsets from a short-word address with a single linear formula
  (`BASE_OFF + (sw - BASE_SW) * 2`) is only valid **within one block's own
  contiguous placement in the blob**; blocks are not laid out contiguously
  in short-word-address order across the whole image. Applying a formula
  calibrated for `blk93` to a `blk88` address decodes *different, wrong*
  instructions at the same nominal address (this happened during this
  session — it produced a spurious apparent second return-jump mid-function
  that a same-file, `sharcimm.decode_all`-consistent re-decode against the
  correct per-block extraction, `blk88_28380548.bin` with
  `base_sw=0x1c02a4`, did not reproduce). Always decode a block from its own
  extracted `.bin` (or verify against `sharcimm`'s depth/sweep tables) rather
  than trusting a reused linear-offset script across block boundaries.
