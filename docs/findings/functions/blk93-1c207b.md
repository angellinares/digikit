# blk93@0x1c207b — per-track smoothed-gain / limiter stage (16 tracks)

- **Bounds**: entry `0x1c207b`, return `0x1c2385` (`9b_abs`, `JUMP(M14,I12)(DB)`,
  `cond=31`, `j=1`), delay slots `0x1c2387` (`15b` restore R15) and `0x1c2389`
  (`25c_rframe`); function ends at `0x1c238a`. **[D]** — agrees exactly between
  `tools/sharcflow.py`'s call/return scan (`flow93.json`: one return in
  `[0x1c207b, 0x1c2385]`, none earlier) and `tools/sharcinv.py`'s classifier
  (`entry=1843323=0x1c207b`, `exit=1844106=0x1c238a`, `n_insns=303`). Span is
  783 sw-units / 303 real instructions.
- **Callers**: `blk93@0x1c2b24` only, from `0x1c3099` (`sharcinv` `callers`
  list and `flow93.json` agree; matches the task's call site
  `0x1c3097`/`0x1c3099` — the `25a_direct` call opcode itself sits at
  `0x1c3099`, two sw earlier than the `15b` load of the argument register R4
  at `0x1c3097`). **[D]**
- **Callees**: `blk69@0xb82d41` (cross-block call, `0x1c220a` → returns
  `0x1c2211`; `blk69`'s base_sw is `0xb80000` per the README, so this really
  is a jump out to block 69) and `blk93@0x1cb3d8`, called **twice**
  (`0x1c2307` and `0x1c231f`). **[D]**
- **Label**: `sharcinv`'s heuristic label is `"block copy / move"` (confidence
  0.4, reason "loads roughly match stores, little compute between them").
  **This disagrees with the decode below** — `compute_total=91`,
  `float_alu=43`, `float_mul=29`, `mac=5`, `shifter=11`, and the constants and
  clip/max/min chain described below are not a copy loop. The label is a
  crude count-based heuristic and is wrong for this function. **[D]**

## What it computes

**[O] interpretive, built on [D] observations below.** The function walks up
to 16 tracks (`float_immediates`/loop-literal evidence, see Structure) and,
for each, runs a chain of `clip Fx by F1` operations (a real SHARC ALU op,
PRM p.13-xx "CLIP", not a tracer gap) against a shared bound register F1,
multiplies several of the clipped values by F4, and combines them with
float add/subtract, a MUL+ADD multifunction op (`Fm=Fxm*Fym, Fa=Fxa+Fya`,
category `0x18`, PGR Table 12-12 p.587) and — at the point the tracer stops —
a MUL+MAX multifunction op (`Fm=Fxm*Fym, Fa=MAX(Fxa,Fya)`, category `0x1e`,
PGR Table 12-12 p.588), immediately followed by a single-function
`min(F1,F8)`. That `MAX(...)` then `min(...,const)` pair is a
saturate-into-range idiom (`clamp(x, lo, hi)` built from two ALU ops), and
`MODE1` bit `0x200000` is explicitly set on entry — functionally consistent
with `REGF_MODE1.ALUSAT` ("ALU Saturation", PRM p.3-36/98-99), though I could
not locate the MODE1 bit-number table to confirm bit 21 is ALUSAT
specifically (**[O]**, worth a second pass).

Six literal float constants appear as immediates in the heavy loop body
(`0x1c21f7`-`0x1c2297` region), confirmed both by `sharcinv`'s
`float_immediates` (plausible=True set) and by decoding the raw `17a`
opcodes by hand:

| bits | value |
|---|---|
| `0x3f58b439` | 0.8465 |
| `0x3e1d14e4` | 0.1534 |
| `0x3f800000` | 1.0 |
| `0x41000000` | 8.0 |
| `0x404a6320` | 3.1623 (≈ √10) |
| `0x3d000000` | 0.03125 (1/32) |

`0.8465 + 0.1534 ≈ 1.0` — a coefficient pair that sums to unity is the
textbook shape of a **one-pole smoothing/crossfade recurrence**
(`y = a*new + (1-a)*old`), one of the shapes named in the task brief
("two-state linear recurrence with state persisted to a caller struct").
`3.1623 ≈ 10^0.5` is exactly the amplitude ratio for **+10 dB**
(`ratio = 10^(dB/20)`), and `1/32` is consistent with a 32-step sub-division
of that 10 dB span (~0.31 dB/step) — i.e. a dB-to-linear gain ladder,
matching `sharcinv`'s own guess of `"envelope or gain"` for the callee
`0x1cb3d8`. **My reading: a per-track gain-smoothing / soft-limiter stage —
clip each of several per-track candidate values into range, blend old/new
with the 0.8465/0.1534 pair, and clamp the result — feeding the callee
`0x1cb3d8` twice per track.** I could not pin down exactly which two
per-track quantities are being blended (state at old-value vs new-target is
my best reading, not confirmed).

Not found here: no FFT-shaped butterfly pattern, no biquad-section shape (no
paired 2-tap IIR coefficient register reuse), no circular-addressed delay
line I could resolve (see Memory — the two `3c`+`16a` blocks before the
`0x1cb3d8` calls set up `dmi/dmm=7/7` circular-mode index/modify registers,
but I only have `0x1cb3d8`'s target address to point at, not a resolved
buffer base — **[O]**), no noise generation, no bit-crush/decimation.

## Structure

**Prologue** `0x1c207b`-`0x1c2103` **[D]**: `I7 += -80` (frame alloc, `19a_scaled`),
then saves I0,I1,I2,I3,I5 (via `5b_move`+`15b` pairs), R14, R15, R10, R11,
R13, M5 into the new frame; sets `MODE1 |= 0x200000`; loads R2 from the fixed
address `0x252534`, a 64-bit pair (R0,R1) from `0x256818`, R4 from `0x252538`.

**Loop-setup census** (all `12a_imm`, i.e. all **literal**, none `12a_ureg`)
across the whole body — `sharcinv`'s vector reports `loop_literal=8`,
`loop_register=0`; static decode of every `12a_imm` found **14** setup sites,
most reusing the identical `count=16, body-span=24 sw` shape:

| pc | count | body span (sw) |
|---|---|---|
| `0x1c20ce` | 16 | 18 |
| `0x1c20ef` | 16 | 59 |
| `0x1c2103` | 16 | 24 |
| `0x1c2151` | 16 | 24 |
| `0x1c2189` | 16 | 24 |
| `0x1c21b6` | 16 | 24 |
| `0x1c226e` | **3** | **94** |
| `0x1c2353` | **15** | 24 |
| `0x1c2390`, `0x1c23b7`, `0x1c23de`, `0x1c2413`, `0x1c243a`, `0x1c2463` | 16 each | 24 |

The `0x1c20ce`/`0x1c20ef` pair zero-fills a 16-entry, 8-byte-stride buffer at
`0x254878...` (confirmed by concrete trace: literal stores of `0` at
`0x254878, 0x254880, 0x254888, ...`). The count=16/span=24 loops recur ten
times through the body and read/write the same 16-entry family of buffers
(see Memory). The **odd one out is `0x1c226e`: count=3, span=94** — this is
the heavy clip/multiply/multifunction network described under "What it
computes"; it is the only loop whose body is long enough to hold that many
distinct compute ops, and its 3 trips is far shorter than the 16-track
loops around it, so it iterates over something else per track (3 unresolved
sub-elements — L/R/mono, or three envelope phases, is my guess, not
confirmed). **[D]** for the counts/spans, **[O]** for what the "3" indexes.

**Outer software loop, register-bounded** — two *conditional* backward
branches (`8a_rel`, not hardware `LCNTR`) were caught by the tracer:
`0x1c2458 -> 0x1c21a7` and `0x1c23ae -> 0x1c21d4`. These re-enter the
`0x1c21a7...0x1c2458`-ish span repeatedly; the tracer forked a new state at
every pass because the branch predicate depends on a register (not a
literal), which is exactly the loop-trip-count ambiguity the task asked to
flag, just realized as an ordinary compare-and-branch rather than a `12a`
loop setup. With `--max-states 1024` the run reached at least 21 passes
before giving up; **I could not establish the real trip count** — 16 (one
per track, using a software loop here because the body already burns the
hardware loop resource on the nested count=16/3 loops) is my working guess,
not proven. **[O]**

**Epilogue** `0x1c2373`-`0x1c238a` **[D]**: restores I0-I5 (`15b`, ureg
16-21), R10, R11, R13, R14 via `15b`, then `9b_abs` return (`cond=31`,
`pmm=6`, `j=1`), with `15b` (restore R15) and `25c_rframe` as the two delay
slots — exactly the return shape the README specifies.

## Memory

All addresses below are literal (`14a`/`14d` absolute, or `17a`/`16a`
immediate loads into I/R-registers), found by decoding every such opcode
across the full 303-instruction body — not by symbolic execution, so
register-relative addresses (`I1+30`, `I4+M4*4`, etc.) that never resolved
to a literal are **not** included and could still hit any table below.

- **Named tables from the task list: no confirmed touch.** I scanned every
  literal `14a`/`14d` address and every literal `17a`/`16a` immediate load
  against the cosine tables (`0x8055c440`/`0x8055c640`), the two 1024-float
  arrays (`0x8055c890`/`0x8055d890`), the 829-float table (`0x8045a6c8`),
  the 32-float table (`0x8045c3c0`), stage 5's `0x26bb68`, the 128-float
  pair (`0x256388`/`0x256588`), the parameter-frame base (`0x2558dc`) and
  every per-track block (`0x2559b6+track*0x60`), and the four audio rings
  (`0x262138`/`0x262938`/`0x263138`/`0x263938`). Zero hits on any of them.
  **This is a negative from partial coverage, not proof** — the function has
  many register-relative loads/stores I could not resolve (`I1+30`,
  `I4+M4*4`, the `3b`-form pre-modify loads, and everything past the
  multifunction-op stop point for the symbolic run). **In particular this
  function does not look like the ring writer** — its loop shape (small,
  16-track, control-rate) doesn't match a per-sample ring traversal, but I
  can't rule it out from indirect stores alone. **[O]**
- **Shared context** `0x252d3c` (the pointer the task names): **confirmed
  used**, loaded as a literal immediate straight into R12 at `0x1c21f7`
  (`17a`, `data=0x252d3c`) partway through the function — it is not read via
  a register argument at entry, the compiler just bakes the known-constant
  address in directly. Two stores land at `0x252d40` (`R12+4`) and `0x252d48`
  (`R12+12`) — this function **writes back into the caller-shared context**,
  the "state persisted to a caller struct" shape. Other literal accesses
  cluster around the same struct: reads at `0x252534`, `0x252538`, `0x25253c`
  (config header before the context proper), `0x2526e8`/`0x2526ec`,
  `0x252718` (byte load, `14d`), `0x252728` (read **four** times —
  `0x1c20e7`, `0x1c212d`, `0x1c2170`, `0x1c23ff` — a flag/mode checked
  repeatedly), `0x252518`, `0x252ae0`. **[D]**
- **Per-track working buffers, not the named parameter frame**: a family of
  literal I-register loads at `0x252c58`/`0x252cb8` (96 bytes apart — same
  stride as the parameter frame's per-track block, but at an unrelated base)
  and a 16-entry array at `0x254778...0x254cf8` (stride shifts from 0x100 to
  0x80 partway through the list) that is zero-filled early (confirmed by
  concrete DM writes during the symbolic run: `0x254878, 0x254880,
  0x254888, ...`, stride 8) and then read/written by most of the count=16
  loops. Separately, a literal I29 load points at `0x252df8`, close to but
  not tied by this pass to either of the above — a third array or an alias,
  not resolved. None of this lines up with the documented parameter-frame
  base `0x2558dc` or per-track block `0x2559b6+track*0x60`. **[D]** for the
  addresses, **[O]** for exactly how many distinct arrays these are.
- **SRC page** (`0x2559b6+track*0x60`, bytes `0x00`-`0x13`): **no literal hit
  anywhere in this function.** Per the task, its consumer must be through a
  register-held pointer if it's read here at all — I found no `17a`/`16a`
  immediate load of any per-track block address either, so if this function
  is the SRC-page consumer, it gets the pointer from a register I never
  traced concretely (the symbolic run stopped at `0x1c22e6`, well before the
  function's later loops). **Open**, not ruled out. **[O]**
- **Near-hit worth flagging**: literal accesses at `0x2558c0`, `0x2558c4`
  (read then written) and `0x2558c8` sit only `0x1c`-`0x24` bytes *before*
  the parameter-frame base `0x2558dc` — possibly a small global header
  immediately ahead of the frame, not part of any per-track block. **[O]**

## Interface

- **R4**: the caller loads it from an `I6`-relative frame slot immediately
  before the call (`0x1c3097`, right before the `0x1c3099` call) — this is
  the one register the orchestrator sets up specifically for this call (the
  `3c`+`16a` pair before every call in the dispatcher is generic
  call-linkage scaffolding, not an argument, since it repeats before every
  call in the orchestrator with the same shape). **[D]**
- **R12**: not read as an incoming argument in the visible prologue; instead
  reloaded mid-function with the literal `0x252d3c` (see Memory). **[D]**
- Ten scratch registers (I0-I5, M5, R10, R11, R13, R14, R15) are
  callee-saved into the local frame and restored in the epilogue — ordinary
  leaf-with-locals convention, not evidence of a wide argument list. **[D]**
- **Callees**: `blk69@0xb82d41` (labelled `"block copy / move"` by
  `sharcinv`, 37 instructions, loads≈stores, no compute — plausibly a
  block-memmove helper) once; `blk93@0x1cb3d8` (labelled `"envelope or
  gain"` by `sharcinv`, 98 instructions, `float_alu=36`, and its own trace
  stub stops almost immediately on an unrelated compute gap) twice per call
  to this function. **[D]**

## Open

- The real trip count of the outer software loop (`0x1c2458->0x1c21a7`,
  `0x1c23ae->0x1c21d4`) — register-bounded, not resolved; 16 (one per
  track) is a guess.
- What the inner `count=3` loop at `0x1c226e` is iterating over.
- Whether the SRC page (`0x2559b6+track*0x60`) is read here through a
  register I never got a concrete value for.
- Whether the two 16-entry arrays near `0x254778` and `0x252df8`/`0x252c58`
  are one struct or several; I only have literal base addresses, not a
  resolved element layout.
- Exact meaning of MODE1 bit `0x200000` — functionally matches ALUSAT by the
  PRM's prose description but I did not find the bit-number table to
  confirm bit 21.
- **Tool gap worth reporting upstream**: `tools/sharc_trace.py`'s
  `_compute()` does not implement multifunction categories `0x1e`
  (`Fm=Fxm*Fym, Fa=MAX(Fxa,Fya)`) or (by the same table, PGR p.588) `0x1f`
  (`...Fa=MIN(...)`) — only `0x18`/`0x19` (add/sub) are modelled. This is
  what stopped every symbolic-trace path through this function at
  `0x1c22e6`/similar sites; every path also needed
  `--allow-provisional-form 14d` to get past an uncertain-but-fully-decodable
  byte-load form first. Neither gap was in the task's listed "known
  remaining gaps".
