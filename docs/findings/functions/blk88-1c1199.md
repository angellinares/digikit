# blk88@0x1c1199 — two-guard scalar mapping: two inlined 1/x (RECIPS+3×NR) plus a 3-coefficient Horner polynomial, not a filter/recurrence

- **Bounds**: entry `0x1c1199`, final return `0x1c1277` (`9b_abs`, `cond=31`
  TRUE, the documented unconditional `JUMP(M6,I4)(DB)` return shape, `pmm=6`
  matching return addressing), delay slots (`25c_rframe`, `2a_short`) finish
  at `0x1c127b`, next function starts `0x1c127c`. **90 instructions**,
  matching `sharcinv.py` exactly (`entry=0x1c1199 exit=0x1c127c n_insns=90`).
  Confirmed independently with `tools/sharcflow.py --base-sw 0x1c02a4` over a
  **freshly re-extracted** `blk88_28380548.bin` (`tools/sharcldr.py
  --dump-blocks`, not the stale scratch copy from an earlier session): the
  return immediately before entry is `{'sw': 0x1c1195, 'after': 0x1c1199}`,
  the one at exit is `{'sw': 0x1c1277, 'after': 0x1c127c}`, no return in
  between. **[V]**
  This function has **two more `9b_abs` jumps through the same `pmm=6`
  (I4/M6) return path in its body**, at `0x1c11af` (`cond=1`=LT) and
  `0x1c1208` (`cond=18`=GT) — genuine **conditional early returns**, not
  counted by `sharcflow.py`'s return list because it only recognizes the
  exact `raw==0x083F343F` (unconditional) return word. Condition-code
  numbers cross-checked against ADSP-2106x SHARC User's Manual Table 3.2
  (`out/refs/50836807228561adsp2106xsharcprocessorusersmanual_revision2_1/all.txt:3778`-`3808`,
  cond 0=EQ,1=LT,2=LE,16=NE,17=GE,18=GT,31=TRUE), the same mnemonic set the
  sibling note `blk88-1c0d68.md` uses. **[V]** for the numbers/positions;
  **[D]** for the mnemonic table's applicability to SHARC+ Type 8a/9b (no
  SHARC+-specific numeric table found in `out/refs`, only the mnemonic-only
  Table 4-20 in the PRM — the classic-core numeric table is the best
  available cross-check).
- **Callers**: **no static caller found**, checked properly for the Type 8a
  blind spot the task warns about. I decoded every `8a_abs`/`8a_rel`
  instruction (not just `25a_direct`/`25a_pcrel`) over freshly re-extracted
  full payloads of **blk93** (`997` Type-8a instructions, `51` with `b=1`
  CALL — this reproduces the task's stated "51 such calls exist in blk93
  alone" exactly, validating the method), **blk69** (`1974` Type-8a, `7`
  CALL) and **blk88** itself (`107` Type-8a, `2` CALL): **zero** of the
  60 CALL-bit instructions across all three blocks target `0x1c1199`. The
  ordinary `25a_direct`/`25a_pcrel` call scan (`715`/`987`/`12` calls in
  blk93/blk69/blk88) also has zero hits. A separate literal scan for the
  address `0x1c1199` (as short-word, ×2, or the `0x28xxxxxx` byte alias)
  loaded via any `17a` immediate in the three blocks — which would reveal
  an indirect-call setup or a jump-table entry — also found nothing. **[V]**
  for "no *static* caller in blk93/blk69/blk88 by either call mechanism or
  literal-load"; **[O]** — 30 register-indirect (`9b_abs` `pmm=5`) call
  sites across the three blocks can't be resolved statically, and the small
  fragment blocks (1/56/76/78/80/91) were not scanned.
- **Callees**: **none** — a genuine leaf. I decoded the function's own 90
  instructions directly (see Structure) and found no `25a_direct/pcrel`,
  no `9b_abs pmm=5` indirect call, and — checking the same Type-8a blind
  spot the task warns about — **both of this function's own `8a` branches
  have `b=0`** (plain conditional jumps, not calls). So unlike the sibling
  primitive at `0x1c06ba` (which this function's own body closely imitates,
  see below), this one does **not call** the shared reciprocal — it
  **inlines the same idiom twice**. **[V]**
- **Label**: inventory label `IIR or recurrence`, confidence 0.5, reason
  "leaf, a few MAC/multiplies with few surrounding adds, writes state back".
  **This label is wrong**, for the same reason `docs/findings/functions/blk93-1cb4b2.md`
  already documented for the shared reciprocal `0x1c06ba` itself: the
  heuristic fires on any dense-MAC leaf, regardless of whether a real
  per-sample recurrence exists. This function has **no hardware loop at
  all** (`loop_literal=0`, `loop_register=0` in the inventory; confirmed
  directly — no `12a_imm`/`12a_ureg` instruction anywhere in the 90-word
  span) and **no dual add/subtract** (`dual_add_sub=0`) — there is no
  per-sample state-update structure here, just dense straight-line float
  compute with three exit points. **[V]**

## What it computes

**[D]** — read via direct per-instruction decode (`tools/sharc_disasm.py`
+ `sharc_trace._compute`, called per instruction rather than through the
stateful tracer — see Open for why the stateful tracer can't get past
instruction #4). Not independently re-verified by a second agent.

This is **not** an IIR filter's per-sample update and **not** a
two-state recurrence. It is a **straight-line scalar-mapping routine**,
called once per parameter change (no loop, so it cannot be processing a
sample block), built from three recognizable pieces:

1. **Two independent inlined reciprocals**, each the exact
   `RECIPS`-seed-then-3×Newton-Raphson idiom the task names for
   `blk88@0x1c06ba` (verified directly against that function too, see
   below) — `float-recips-seed` followed by three repeats of
   `float-multiply ; float-mulalu-subtract` (the documented `x_{n+1} =
   x_n*(2 - a*x_n)` refinement, `2.0` literal present at both sites,
   `0x1c11c2` and `0x1c1257`). First block: `0x1c11c5`-`0x1c11d3`
   (seed `R1=recips(R12)` at `0x1c11c5`, 3 NR rounds, result chain ending
   in `R4`). Second block: `0x1c1252`-`0x1c1267` (seed `R1=recips(R0)`,
   3 NR rounds, result chain ending in `R12`). **[V]** for the
   instruction-level match (opcode-for-opcode identical shape to
   `0x1c06ba`'s `0x1c06c0`-`0x1c06e9`, which I also disassembled — see
   below); **[O]** for what value is actually being inverted each time
   (register contents are `Unknown` in an unstated-argument decode; not
   traced from a concrete caller).
2. **A 3-coefficient Horner-style polynomial**, evaluated with the
   literal coefficients `-0.19033339619636536` (`0x1c11b4`),
   `-7.137931823730469` (`0x1c11b9`), `-42.82770919799805` (`0x1c11bd`)
   loaded one at a time into `R1` and each immediately combined
   (`F1*F2->R4`, then `F4+F1->R4`, then `F2+F1->R12`) — the load-then-
   combine-then-overwrite pattern is the standard compact Horner form on
   this ISA (one live coefficient register, one running accumulator).
   These are not power-of-two or otherwise "clean" constants, unlike the
   `1/16` seen in `0x1c0d68` or the `1/12` semitone fraction seen at that
   primitive's call sites — they look like a **curve-fit** (e.g. a
   parameter-warp or coefficient-shaping polynomial), not a known DSP
   constant. **[O]** — no physical meaning established for these three
   numbers.
3. **Two guard branches gating expensive work**:
   - `0x1c11ac`: `compare(R8, 0.000244140625)` (`2^-12`, loaded at
     `0x1c11a9`) immediately followed by the conditional return at
     `0x1c11af` (`cond=LT`): **if `R8 < 2^-12`, return immediately**,
     skipping the entire body. This is the classic "reject a
     near-zero/degenerate divisor before reciprocating it" guard, and it
     directly precedes the first inlined reciprocal — strong evidence
     `R8` (or a value derived from it) is the operand of that `1/x`.
     **[D]**
   - `0x1c11a6` (`8a_rel`, `cond=GT`, `b=0`, `reladdr=63`, target
     `0x1c11a6+63=0x1c11e5`, computed with the same signed-24-bit
     PC-relative formula `sharcflow.py` validates for `25a_pcrel`): if
     `R8-1.0 > 0` (i.e. `R8>1.0`), **skip straight past the eps-guard and
     the first reciprocal/polynomial block** to `0x1c11e5`, the point
     where both paths reconverge. `0x1c11eb` (`8a_abs`, `cond=GT`,
     `b=0`, absolute target `(28<<16)|4727 = 0x1c1277`) is a second,
     later gate that can jump **directly to the function's own final
     return**, skipping the second reciprocal and the rest of the
     polynomial work entirely. **[V]** for both targets (decoded and
     hand-verified against the two addressing formulas); **[O]** for the
     exact predicate meaning (`R8` vs. `1.0` boundary, `R2=R8-1.0`
     computed at `0x1c119d`/`0x1c11a3` right before the first branch).
   Net shape: **`if R8<=eps: return early; if R8>1.0: skip the general
   case; else: run the general case (guard #2, polynomial, first
   reciprocal); [reconverge]; if <second guard>: return early; else: run
   the rest (second reciprocal, more polynomial terms, final combine)`.**
   Three narrow ranges of `R8` get progressively cheaper paths — a shape
   much more consistent with clamping/special-casing a **user-facing
   parameter** (silence/degenerate value, "no scaling needed" value, and
   the interesting middle range) than with any per-sample filter math.

**Cross-check against `0x1c06ba` (the task's named shared reciprocal)**: I
disassembled `0x1c06ba` directly (47 instructions, matches `sharcinv.py`)
and it has the *identical* `float-recips-seed` immediately followed by
three `float-multiply`/`float-mulalu-subtract` pairs at `0x1c06c0`-`0x1c06e9`
— **and it also carries the same "IIR or recurrence" inventory
mislabel**, already corrected in `docs/findings/functions/blk93-1cb4b2.md`
("that label is wrong ... shared `1/x` subroutine, not envelope state").
`0x1c06ba` differs from `0x1c1199` in one structural way: it has a real
`12a_ureg` hardware loop near its tail (register trip count, not literal)
that `0x1c1199` does not — consistent with `0x1c06ba` being a
general-purpose reciprocal *plus* a small bulk-copy/setup loop callable
from many places, while `0x1c1199` is a bespoke one-shot mapping that
inlines the reciprocal rather than paying a call. **[V]**

**If the inventory's "IIR or recurrence" label is meant literally (a
digital-filter coefficient recurrence)**: nothing here supports that —
no loop, no per-sample state advance, no dual add/subtract, no ring-buffer
touch (see Memory). The best-supported alternative is a **scalar
parameter-mapping/coefficient-shaping function** (input `R8`, likely also
`R0`/`R4` as auxiliary inputs, output not traced to a caller — see
Interface), built from guard branches + polynomial + reciprocal(s). Whether
its *output* ultimately feeds a filter's coefficients elsewhere was not
established. **[O]**

No loop of any kind (`12a_imm`/`12a_ureg`) anywhere in the 90-instruction
span — checked directly over the full decode, matching the inventory's
`loop_literal=0, loop_register=0`. **[V]** No prologue register-save: no
`I7`-frame setup (`19a_scaled`), no `15b`/`3c` push sequence at entry,
unlike the normal callee-saves prologue seen in `blk93-1cb4b2.md`'s
function or the 10-instruction fused push prologue in `blk88-1c0d68.md`.
This function freely clobbers `R0,R1,R2,R4,R8,R12,B4,I4,M4` and restores
nothing. **[V]**

## Memory

Four addresses, all in a tight `0x241268`-`0x241280` range (**8-byte
stride, 4 entries**), touched via `14a` (explicit literal address) or a
literal-loaded `I4` pointer:

| address | how touched | role (structural guess) |
|---|---|---|
| `0x241268` | `14a` load -> R0, at `0x1c11e5` (the GT-skip convergence point) | read on entry to the "late" path |
| `0x241270` | `14a` load -> R0, at `0x1c11f2` | read, combined with R8 (`R8=R8+R0`) |
| `0x241278` | `14a` load -> R0, at `0x1c126a` | read, near the final combine |
| `0x241280` | `I4` literal-loaded at `0x1c11fb`, `M4=2` set alongside, used for at least one more indexed `DM(I4,M4)` access at `0x1c1203` | pointer walk continuing the same stride |

This is the same general `0x241xxx` RAM scratch page as `0x2411c8`-`0x241234`
documented in `blk88-1c0d68.md` (three "state cells" for the shared
exponential primitive), but a **different, non-overlapping** address
range — consistent with a shared per-DSP-instance scratch area used by
several of blk88's small primitives, each claiming its own few cells,
rather than a single struct. **[V]** for "these four addresses, this
function, this range"; **[O]** for whether they are read-only constants or
mutated state (only loads were identified here; the `3b`/`4a` pair at
`0x1c1203`-`0x1c1205` could hide a parallel store I did not fully decode).

**No named table touched**: none of the cosine tables (`0x8055c440`/
`0x8055c640`), the 1024-float pair (`0x8055c890`/`0x8055d890`), the
829-float exponential (`0x8045a6c8`), the 32-float table (`0x8045c3c0`),
`0x26bb68`, the 128-float pair (`0x256388`/`0x256588`), or any audio ring
(`0x262138`/`0x262938`/`0x263138`/`0x263938`) appears as a literal operand
anywhere in the 90-instruction span — checked by enumerating every
`17a`/`14a` literal directly (not by trusting the inventory's
`named_tables_touched=[]` alone, since that only scans a subset of literal
forms). **[V]**

**Does not touch the parameter frame**: no literal anywhere in this span
falls in `0x2558xx`-`0x2560xx` (base `0x2558dc`, per-track
`0x2559b6+track*0x60`). All literal addresses found are in the
`0x241xxx` scratch page. **[V]**

One suspicious literal: `0x1c11ee` loads `R2 = 0x001c1251` — the
inventory's literal scanner flags this as an "implausible" float
(`2.58e-39`, subnormal) because it is not a plausible float bit pattern,
and correctly so: **`0x1c1251` falls inside this very function's own
instruction span** (between `#073` and `#074`). It is very likely a code
address, not a float constant, but no consuming instruction (indirect
jump/call through `R2`) was found before `R2` is overwritten — **[O]**,
not resolved.

## Interface

`R8` is the clearest live-in argument: it is read immediately (`R2=R8-1.0`
at `0x1c11a3`, guarding branch `0x1c11a6`) and guarded against
`R8<2^-12` right before the first inlined reciprocal (`0x1c11af`) — strong
evidence `R8` is (or scales) the value being reciprocated, and that the
guard exists specifically to protect that `1/x`. `R0` and `R4` are also
read as live-in values in the very first instruction (`R4=F4+F0` at
`0x1c119d`), consistent with the task's "R4/R8/R12" convention, though
which of `R0`/`R4`/`R12` (if any) carries the actual `R12`-slot argument
was not established — this function's `R12` is set to a **local
constant** (`0.000244140625`) at `0x1c11a9`, one instruction after entry,
so if `R12` arrives with caller data it is immediately discarded. **[O]**

No `I`/`M`-register pointer argument is set up before any use — `I4`/`M4`
are set to **literal** addresses inside the callee (`0x241280`/`2`), the
same "hard-coded scratch, not a caller-supplied pointer" pattern
`blk88-1c0d68.md` found for its own state cells. No per-track struct
pointer convention (no read near `0x2559b6+track*0x60`) — this does not
look like the "per-track gain smoothing" shape.

**Output register**: not established. The function's last compute before
the final return is `R0 = F0*F2` (`0x1c1276`), which — together with `R0`
also being the destination of the two other exit-adjacent computes
(`0x1c1270` compare, `0x1c1273` `R0=F4+F8`) — makes `R0` the best
candidate for the return value, but this was not confirmed by any
caller-side read (no caller found at all, see Callers). **[O]**

## Open

- **Stateful tracing stalls immediately.** `tools/sharc_trace.py --blob
  --start 0x1c1199 --concrete-memory --assume-32bit-normal-words
  --follow-loaded-calls` stops after 3 steps at `0x1c11a0` on
  `unsupported full compute cu=0x0 opcode=0xe0` — this opcode is not
  `0xd9`/`0xda` (the task's named gaps) but a third undocumented float ALU
  opcode. It recurs as the function's very last instruction
  (`0x1c127a`, a return delay slot). Resolving `0xe0` (and the
  `multifunction category=0x1c` at `0x1c126d`) against a public source
  would let the stateful tracer actually walk this function's branches and
  confirm the guard predicates and output register with concrete/symbolic
  values instead of per-instruction structural reading.
- **What the three polynomial coefficients
  (`-0.19033339619636536, -7.137931823730469, -42.82770919799805`) mean.**
  Not power-of-two, not any previously-named engine constant. Could be a
  curve fit for a parameter-warp (e.g. a knob-position-to-coefficient
  mapping); not derived here.
- **What the two reciprocals actually invert**, concretely — `R8`
  (guarded by the eps check) is the best candidate for the first; the
  second reciprocal's seed reads `R0` at `0x1c1252`, but what `R0` holds
  at that point (after ~50 intervening instructions on two different
  paths) was not traced end to end.
- **The `0x241268`-`0x241280` scratch cells' contents and whether anything
  else in the image writes them** — not searched (`tools/refscan.py` over
  that range would answer it, as it did for `blk88-1c0d68.md`'s cells).
- **The `0x1c1251` literal** loaded into `R2` at `0x1c11ee` — falls inside
  this function's own span; not resolved as a jump-table entry, a stray
  code reference, or coincidence.
- **No caller found in blk93/blk69/blk88** by either call mechanism
  (including the Type 8a fix this task applied) or by literal-address scan.
  Either this function is reached only through one of the 30 unresolved
  register-indirect call sites in those blocks, is called from one of the
  small fragment blocks (1/56/76/78/80/91, not scanned here), or is
  currently dead code in this build — an empty caller list is not proof of
  the latter (per the repo's own rule).
