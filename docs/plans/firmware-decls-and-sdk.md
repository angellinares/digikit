# Firmware declarations, module SDK and Syntakt

Started 2026-10-27. Targets: DT2 OS 1.17, DN2 OS 1.12, Syntakt OS 1.42.

## Goal

1. Write each firmware fact (function, table, struct field) once, in one typed declaration. Generate rules, Rust, C and
   assembly from it.
2. Give content-module authors plain C against generated headers, with fast builds.
3. Make a module a readable source package that people share, and that the desktop and web Transfer tabs build and
   send to the device. Users never handle `.dkm` files.
4. Use the Syntakt as the third device that proves the SDK is device-agnostic.

## Decisions (Em, 2026-10-27)

- core/* adapters and the runtime stay Rust. Content modules use a C ABI contract, and C is the first-class language.
- SHARC DSP code stays assembly. C on SHARC is a bounded pilot (step 7). selcc puts every local in a stack slot:
  15 instructions per element against 3 by hand (`docs/findings/20-patch-toolchains.md`).
- No Rust proc macros. `module.toml` stays the authored manifest, and a per-module header is generated from it.
- Catalogue the firmware first, then design the declaration format against what the catalogue finds. Declare an anchor
  when a feature uses it, not all candidates up front.
- Syntakt: ColdFire CPUs only. Never modify, emulate or reconfigure the FPGA (syx section 1). DT2/DN2 come first; the
  Syntakt emulator boot waits until after step 9, and steps 3 and 9 report a portability count on 1.42.
- The anchor reference is generated by `patchkit gen` from the declarations and shown as a searchable page; the review page stays a separate tool for undeclared candidates.

      `docs/sharc/SOURCES.md`): 2x oversampling with a half-band decimator, per-sample parameter ramps, circular-buffer

      copied into the repo.
- [x] A short style guide for readable SHARC assembly (`docs/sharc/style.md`) (register naming, macros, block-loop layout).
- [x] SDK DSP kernels in `sdk/dsp/`, included into each module (no shared copy yet): step macros for a module's own

      instruction ceiling). Then pluck's string loop is rebuilt from them (target about 10 instructions per sample,
      from 23). Decision: no comparison with calling the firmware's own kernels (finding 72: own kernels win; a stock
      import needs per-device DSP import rows).

      `_dk_halfband_down` (23 taps, -38 dB, 21.8 per output), bit-exact on the core. Open, proposed to Em: drop the
      pluck rebuild (pluck uses an allpass fractional delay, so it would change its sound) and use the kernels in the
      machine and fx templates instead.
- [ ] (Open, proposed to Em: drop, since Em wants to replace Selache, `selcc` included; SHARC code stays
      assembly.) C pilot as glue only (half a day): pluck's `note_on` and parameter mapping in C (`selcc`) behind a frame shim,
      calling the kernels; measure instructions per note-on and code size; decide whether `module:new` offers C for
      SHARC glue. No C sample loop (finding 20 measured 46 against 6-7 instructions per sample).
- [ ] Emulator follow-ups found in step 7: `cargo test -p sharc-native --lib` aborts in
      `fast::lower::tests::flat_access_*` (a Cranelift "fill your block before switching" panic, also on the commit
      before step 7); the fast-vs-core differential vectors never set `assume_nw32`, so the (nw) 19a guard is covered
      by the Python tests only.
      Two assembler/decoder points from the delay and half-band kernels: `MODIFY(Ix, My)` (register modifier) was a `selas`
      mis-encoding (missing Type 7b fixed bits; fixed in the Selache fork, finding 20); open: Selache lists short
      load/store forms with M0-M3 outside a DO loop as 4-byte rows, which the verify step rejects (kernels use M4).
- [ ] Own SHARC+ assembler (follow-up after the kernels): replace Selache `selas` with an assembler built from our
      encoding table (`tools/sharc_dev/sharcspec/decode_table.json`, `compute_table.json`, from the manuals in
      `out/refs`). Write it in Rust next to the generated decoder (a new Rust package, working name sharcasm), so a wasm
      build stays possible. It parses text by our printer's templates and accepts the `selas` dialect that module
      sources use; it encodes by inverting each form's fields, with fixed rules where several encodings print the same
      text (short loops are 48-bit ISA). Proof: every instruction of the DT2 1.17 and DN2 1.12 images decodes, prints
      and assembles back to the same bits (ambiguous forms listed), and every module and kernel source assembles to
      the bytes `selas` produced. Then `pk_sharc` uses it and `selas` becomes a cross-check only. Payoff: no GPL
      dependency, no `selas` mis-encodings, an assembler that can run in the browser. Cost about 2-3 days; confidence
      high (the corpus test).

Proof: kernel tests against the reference models and instruction ceilings on the concrete core; hardware cycles are not
measured (the emulator counts instructions, not stalls).

Rules (kernels, from the public manuals and the firmware, see docs/sharc/style.md): block loops of 4 or more
instructions; B/L only on I0-I5 with L back to 0 on every exit, L6/L7/B6/B7 untouched, B3 saved if written; no DAG
register load within 4 instructions of its use; data in DM only.

Decision: offer `--lang c` for SHARC glue, or keep assembly only.

Study 2026-10-27 ([docs/findings/72-sharc-kernels-1-17.md](../findings/72-sharc-kernels-1-17.md), static): kernels to
build first are (1) ramp, gain and mix, (2) biquad over 32 samples, (3) circular delay with interpolated read (the
stock delay takes about 41 instructions per sample without hardware circular buffers; about 15 looks possible),
(4) soft saturator with ramped drive, (5) reciprocal, rsqrt and divide macros. Own kernels beat the stock ones on
the hot path; a stock import pays only for the divide. `pluck.s`'s string loop is 23 instructions per sample; about
8-10 looks possible. Open: short DO loops, whether modules may set B/L for circular buffers, one shared kernel copy
across modules.
