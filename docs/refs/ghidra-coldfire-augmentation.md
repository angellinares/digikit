# Ghidra ColdFire augmentation for MCF5441x

## Executive answer

**Yes—materially, and with a bounded first target.** Public NXP manuals plus Ghidra's Apache-2.0 68000 language are enough to turn the current generic ColdFire/EMAC fork into an MCF5441x-specific language with better instruction boundaries, register names, control-flow continuity, and P-code for the EMAC instructions actually encountered. This should be done as a small, separately measurable ColdFire stream; it has a higher near-term payoff than further broad SHARC language work because a single undecoded CPU instruction can terminate Ghidra flow recovery, but it does not replace the SHARC work or establish firmware facts.

The target is the MCF5441x's Version-4 ColdFire core with MMU and EMAC, not a generic 68040/FPU machine. NXP's product material calls the family V4e, while an NXP Tower document and historical U-Boot commit call it V4m; use the authoritative MCF54418 reference manual's feature/register tables and emitted instruction tests rather than treating either label as a complete feature mask. The independently maintained Buildroot target explicitly records the operationally important constraint: MCF5441x has an MMU and no hardware FPU. [NXP data sheet](https://www.nxp.com/docs/en/data-sheet/MCF54418.pdf) [NXP reference manual](https://www.nxp.com/docs/en/reference-manual/MCF54418RM.pdf) [Buildroot MCF5441x configuration](https://lists.buildroot.org/pipermail/buildroot/2026-April/800822.html)

## Current gap

* **High — decoding/control-flow barrier:** the local extension, `tools/ghidra/ColdfireEMAC/data/languages/68000_emac.sinc`, documents and fixes `movclr.l ACCy,Rx` plus several EMAC operand/accumulator errors. Its README says stock Ghidra lacks a `movclr` constructor, which turns such instructions into bad instructions and stops flow analysis. This is already concrete evidence that ISA-specific work changes analysis reachability; upstream's current `coldfire.slaspec` is only a two-define wrapper around shared `68000.sinc`. [local extension README](../../tools/ghidra/ColdfireEMAC/README.md) [upstream wrapper](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/68000/data/languages/coldfire.slaspec)
* **Medium — wrong CPU superset:** shared `68000.sinc` exposes 68040-style FP registers/instructions and many 68k MMU/cache control registers under the ColdFire build, while the MCF5441x public data sheet lists core+EMAC+MMU, not an FPU. This can make impossible line-F encodings look like instructions and names some control-register transfers with non-MCF semantics. Keep an MCF5441x feature mask (not merely `@define COLDFIRE`) and reject unsupported coprocessor/FPU forms. [upstream registers and constructors](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/68000/data/languages/68000.sinc) [NXP data sheet](https://www.nxp.com/docs/en/data-sheet/MCF54418.pdf)
* **Medium — incomplete/incorrect privileged-state model:** the local `ctlreg` table is inherited from upstream and has generic/unknown fallbacks; it lacks an explicit MCF5441x register map and contains a suspicious `SRP` constructor that exports `BUSCR` in the copied source. Do not silently treat this as an observed firmware bug, but audit every `movec` encoding against the MCF54418RM and the GNU MCF54418 control-register table before assigning P-code/register names. GNU's MCF5441x addition specifically added ACR4–ACR7 and RGPIOBAR, demonstrating that chip-specific control-register names are required. [local table](../../tools/ghidra/ColdfireEMAC/data/languages/68000_emac.sinc) [GNU MCF5441x support patch](https://sourceware.org/legacy-ml/binutils/2009-11/msg00000.html)
* **Medium — semantics and ABI are generic:** the extension intentionally leaves `movclr` saturation, ACCext clearing, and MACSR PAV side effects as a userop/TODO. Its `68000.cspec` is also a generic stack ABI and includes FP returns. That is adequate for initial disassembly, not trustworthy decompilation of DSP/EMAC-heavy routines or a proven compiler ABI. [local README](../../tools/ghidra/ColdfireEMAC/README.md) [local compiler spec](../../tools/ghidra/ColdfireEMAC/data/languages/68000.cspec)

## Primary sources

### ISA, privileged state, and peripherals

1. **NXP MCF54418RM (MCF5441x Reference Manual, Rev. 5)** is the controlling public specification: chapter 1 describes the Version-4 core, chapter 4 the MMU, chapter 5 the EMAC and its instruction summary, and later chapters give the interrupt controller/vector and peripheral register maps. Translate encodings and architectural effects from this document first; apply the matching chip errata when a behavior matters. [MCF54418RM](https://www.nxp.com/docs/en/reference-manual/MCF54418RM.pdf) [MCF54418 errata](https://www.nxp.com/docs/en/errata/MCF54418DE.pdf)
2. **NXP CFPRM** is the public family-level reference for user/privileged programming models, integer/EMAC/FPU instruction descriptions, exceptions, and control-register architecture. It is useful to cross-check the family ISA, but the device RM wins where it differs or where an optional unit is absent. [CFPRM](https://www.nxp.com/docs/en/reference-manual/CFPRM.pdf)
3. **NXP MCF54418 data sheet** confirms that all listed MCF5441x variants provide the Version-4 core with EMAC and MMU. It is a concise feature gate, not a substitute for instruction semantics. [MCF54418 data sheet](https://www.nxp.com/docs/en/data-sheet/MCF54418.pdf)

### Upstream Ghidra and extension structure

1. Upstream Ghidra's 68000 processor module has a language-definition file (`68000.ldefs`), per-variant `.slaspec` wrappers, shared `68000.sinc` register/decode/P-code definitions, processor spec, and compiler specs. The ColdFire wrapper selects the shared file via `COLDFIRE`; it is not an MCF5441x model. The correct augmentation is therefore another language module/variant with an `.ldefs`, `.slaspec`, copied-or-included common definitions, `.pspec`, and `.cspec`, compiled to `.sla`—the shape already used locally by `tools/ghidra/ColdfireEMAC`. [language definitions](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/68000/data/languages/68000.ldefs) [shared SLEIGH](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/68000/data/languages/68000.sinc) [Ghidra skeleton module guidance](https://github.com/NationalSecurityAgency/ghidra/blob/master/GhidraBuild/Skeleton/data/README.txt) [SLEIGH specification](https://github.com/NationalSecurityAgency/ghidra/blob/master/GhidraDocs/languages/html/sleigh.html)
2. There is usable upstream work but no discovered upstream MCF5441x language: Ghidra issue [#905](https://github.com/NationalSecurityAgency/ghidra/issues/905) reports the ColdFire `mov3q` zero-means-minus-one decode error; PR [#4270](https://github.com/NationalSecurityAgency/ghidra/pull/4270) implements ISA-C `BITREV`, `BYTEREV`, and `FF1`; PR [#9081](https://github.com/NationalSecurityAgency/ghidra/pull/9081) audits shared 68000 flag P-code. Rebase/check these before carrying any local change. None is evidence that MCF5441x EMAC/MMU is fully modeled.

## Recommended plan

1. **Baseline inventory before editing.** Preserve the existing `68000:BE:32:ColdfireEMAC` run and record, in a repeatable JSON/SQLite report under `out/`, instruction starts/bytes decoded, bad-instruction starts, function starts, and flow/call-reference counts. Use `tools/ghidradump.py`, `tools/ghidraq.py`, `tools/codeseeds.py`, `tools/entryhist.py`, and `tools/refscan.py`; do not infer absent callers from Ghidra alone. Add a ColdFire analogue of `tools/sharcpcode.py measure/compare` if the current tools do not produce this delta.
2. **Publish a manual-derived feature matrix.** In a committed source/test file (not firmware output), enumerate each candidate opcode/control register: MCF5441x availability, instruction words/length, operands, reads/writes/flags/exceptions, NXP manual page/section, and independent GNU/QEMU status. Start with `movclr`, all MAC/MSAC load forms, accumulator moves, MACSR/MASK/EMACSR, `movec`, cache/MMU control, `halt/stop/rte`, interrupt/vector-relevant instructions, and `mov3q`. Explicitly mark FPU/coprocessor forms unavailable for this chip.
3. **Keep the language local and small initially.** Extend `tools/ghidra/ColdfireEMAC/data/languages/` into a distinct `68000:BE:32:MCF5441x` variant rather than mutating stock `68000.sinc`; update its `.ldefs/.slaspec/.pspec/.cspec`, compile through `tools/ghidra/install-coldfire-emac.sh` (or its renamed general installer), and retain stock and EMAC baseline languages for comparison. Add MCF control registers with NXP names/encodings, remove/guard impossible FPU constructors, then add P-code only where a manual table and tests establish effects.
4. **Use synthetic public test vectors.** Hand-write a compact `.s`/expected-byte corpus from the NXP manuals, including positive and negative feature-mask cases, all accumulator selection bits, `movclr` side effects, `movec` control-register names, privileged flow/exception instructions, and `mov3q #0` meaning -1. Assemble with GNU as a *separate* oracle; test SLEIGH decode/length/operand order/P-code against the handwritten expected results. Never use firmware bytes as fixtures.
5. **Measure semantics separately from coverage.** Compare baseline/new Ghidra reports: fewer bad instructions, recovered instruction bytes and basic blocks, function-body continuity after previously failing starts, references and decompiler completion. For P-code, test register/flag/ACC effects with Ghidra's emulator only if a static test cannot prove the lift. Check `git diff`, compile SLEIGH, and run `uv run --with pytest python -m pytest tests -q`.
6. **Upstream only clean, generic changes.** Submit narrowly scoped upstream PRs (e.g., `mov3q`, generic EMAC decode/P-code defects, shared flag fixes) with manual-derived tests. Keep MCF5441x peripheral maps, loader assumptions, and ABI hypotheses local unless they are generally applicable. Start review from upstream [`68000.sinc`](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/68000/data/languages/68000.sinc), [`coldfire.slaspec`](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/68000/data/languages/coldfire.slaspec), and local [`68000_emac.sinc`](../../tools/ghidra/ColdfireEMAC/data/languages/68000_emac.sinc).

## Expected payoff and limits

**Expected payoff:** correct EMAC decoding immediately prevents local control-flow truncation; chip-accurate `movec`/MMU/cache/interrupt register names make exception setup, vectors, and MMIO/peripheral annotation more legible; correct P-code yields better data flow and decompilation around accumulator routines. A chip-specific compiler spec can improve function signatures only after public ABI evidence and independent observations support it.

**Limits:** SLEIGH cannot identify data as code, repair missing seeds, recover computed calls, model board wiring/peripheral behavior, prove a calling convention, or validate a label against firmware. It cannot make the MCF5441x CPU augmentation help SHARC+ decoding, loader mapping, or SHARC decompilation. Thus the first ColdFire stage is likely the best immediate analysis-quality return (removes hard decode barriers), whereas SHARC work remains the larger independent coverage/semantic project. All conclusions here are source-survey recommendations, not `[V]` reverse-engineering findings.
