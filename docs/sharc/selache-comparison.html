SHARC+ VISA decoding · ADSP-21569 · Digitone II 1.11 main program

Selache against the firmware

An independent open-source SHARC+ toolchain, js216/selache, run on the same DSP bytes as digikit's tools/sharc_disasm.py. Both are scored against the one oracle that doesn't depend on either decoder: the firmware's own call sites.

2026-09-19 selache @ 2b26d3b digikit @ a5643ba images: DN2 1.10E, 1.11 · DT2 1.15C, 1.16

What came out of it

  • Two table fixes, adopted in this PR. Type 2b goes back to the PGR prefix 000000011, and Type10a_rel is decoded in VISA. On four images the known-boundary walk lands 191–261 more spans exactly, never overshoots, and sharcpcode compare reports 0 regressions.
  • selache's instruction lengths are the stronger of the two today: 99.0% of spans land exactly, against 84.3% for the current table. But VISA resynchronises fast, so a walk that starts 2 bytes off still lands 94.9%. The margin is real but modest.
  • digikit is right where selache is not in most of the 0x0000–0x007F family, which digikit's firmware-derived form reads as 16 bits and selache as 48, and in Type 4a, which selache shortens to 32.
  • Disassembly text is not a round-trip format. Only 83.9% of unique instructions reassemble to identical bytes. Patches must be written as source and verified by re-decoding, never edited as disassembly.
  • selache stays outside digikit. It is GPL-3.0 and digikit is GPL-2.0, so no code or tables move across. It is used as an external oracle and authoring tool.

The oracle

Every absolute cjump (0x1804 + 24-bit target) is found by a byte scan that needs no decoder: 1,606 sites on DN2 1.11, all inside the two code regions, none in 6.2 MB of data. Each site is an instruction start, and so is each target (461 function entries). Between two consecutive known starts, correct lengths must sum exactly to the distance. A walk can stop at a word it cannot size, land exactly, or overshoot. The test can come out either way, which a "percent decoded" figure cannot.

Every figure below also has a control: the same walk started 2 bytes late, or random targets in place of decoded ones. Without it, VISA's self-synchronisation would make any decoder look good.

selache's walks never stop, so an unknown word costs it an alignment guess rather than the rest of the function. That also means it can walk confidently through data. Its misses cluster on if av, if flag0_in and if nbm jumps, which is what data decoded as code looks like.

Along digikit's walks, the two decoders give different lengths for 2,667 of 27,542 instructions (9.7%). For each one, both lengths were tried and the walk continued to the next known start. tools/sharcpcode.py compare before → after: 0 regressions; aligned instructions that decode 21,792 → 22,825 on DT2 1.16 and 21,361 → 22,678 on DN2 1.11, with no length differences against the generated language. The digikit test suite fails the same 22 environment-bound tests before and after. The three new tests fail on the stock table and pass with the fix.

Left open on purpose. Type10a_abs (110) competes with Type 2c (1100) for 0xDxxx words. Read either way, those words land the same number of extra spans (six on DN2 1.11), so this test cannot choose, and the PR does not. selache reads all of 110x as 16-bit Type 2c.

So its disassembly is a reading aid, not a patch source. Its assembler is sound for code written from scratch, which is the useful direction.

The boot stream, checked from the other side

A four-instruction program was assembled, linked at VISA 0x180000 and turned into an LDR by selache's selload. An independent boot-stream reader parsed it back into exactly the linked sections. The code sits at byte address 0x28300000 = 2 × 0x180000 + 0x28000000, with 0xAD-signed headers that XOR to zero and LE words, MSB word first. That is the §2 address model, confirmed by a producer rather than inferred from a consumer.

Proposed integration

Selache enters as a tool beside the pipeline, never as a dependency inside it.

Oraclenow

Second decoder, scored by the firmware

Build selache out of tree (Linux or WSL, cargo build --release). A 30-line harness prints selache's length and text for every even offset of a region. The known-boundary walk scores it next to sharc_disasm.py, with the late-start control.

Differentialper table change

Disagreements become table fixes

Where the two disagree and the walk decides, the firmware measurement goes to build_table.py with a test, as in this PR. selache is cited as corroboration, never as the source. Next candidates: the 0x00xx and 0x02xx undocumented families, and 0xDxxx.

Authoringfor DSP patches

New code from source, spliced into section 7

Write the patch in assembly or C, then build it with selas/selcc and seld, using an LDF that describes only the free region. Re-decode every emitted instruction with both decoders, and write the bytes into the matching boot-stream block. Never round-trip through disassembly text.

Whole programslater, gated

selload for complete boot streams

Validated here on a toy program only. Anything that replaces a DSP program on an instrument first needs the ColdFire side's upload path understood, and a recovery path proven.

What selache is

Tools

selas assembler, selcc C99 compiler, seld LDF linker, selload ELF → LDR, seldump, selpatch, selmem and friends, plus selinstr: encoder, disassembler and VISA compression. Rust, one workspace.

Licence and limits

GPL-3.0; its C library is MIT. Its width rule reads at most two words, with one word1 & 0x3F ≥ 0x38 test for the ambiguous families (the same bits as digikit's 4b). It has ??? fallbacks and a few forms its own authors mark uncertain.

Firmware and anything derived from it stays out of this repository. The bytes quoted above are the output of an assembler run on four lines of our own source.

Method and numbers: docs/sharc/SPEC-FINDINGS.md §3.4–3.5, docs/FINDINGS.md. Measured with scripts/sharc_selache_compare.py and its selache harness in angellinares/dn2_firmware_explore, which also carry the integration notes for that repository.
